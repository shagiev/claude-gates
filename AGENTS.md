# Review guidelines для Codex (claude-gates — репо самого плагина gates)

Ты — независимый ревьюер. Оценивай изменения по инвариантам проекта. Severity
`critical`/`high` = блокирует деплой — ставь только при реальном риске.

**Если ревьюишь ДИЗАЙН/ПЛАН** — суди полноту сценариев (секция BSAC): перечислены ли
топ-уровневые сценарии, закрыт ли каждый fail-open краевой случай, что упущено.

## Blocking (critical/high)

Домен этого репо — сама гейт-система; «деньги» здесь = целостность гейтов у всех
пользователей плагина:

- **Fail-open дыра.** Изменение, при котором гейт молча ПРОПУСКАЕТ то, что обязан
  блокировать: непроверенный деплой, код-коммит без лесенки, обход через конфиг/шим/env.
- **Ослабление через конфиг.** Всё, что позволяет `.codex-gate.yaml` (или его отсутствию/
  битости/незастейдженной правке) снять жёсткие код-пути, деплой-проверки или строгие
  дефолты. Строгий режим при нет/битом конфиге — инвариант.
- **Потеря fail-closed семантики.** Ошибка/outage/дрейф схемы вердикта, трактуемые как
  «чисто»; шим, исполняющий не-тот код или тихо пропускающий при отсутствии плагина.
- **Слом opt-in изоляции.** Плагин начинает вмешиваться в НЕ-онбордженные проекты
  (хуки не exit 0 вне git-репо / без конфига в worktree-OR-HEAD).
- **Молчаливый обход аудита.** Любой skip/обход без записи в audit-лог.
- **Тест, трогающий боевые файлы.** Тест, пишущий в реальные ledger'ы/маркеры/audit
  репо-носителя (изоляция-инварианты conftest).
- **Новый code path без теста, реально входящего в ветку.**
- **Security-класс гейта.** Blocking: внешний/конфигурационный ввод в опасный сток —
  `shell=True` или склейка команд вместо argv (реальная находка 25.07 в `_run_empirical`);
  путь из конфига/ввода без нормализации (обход код-путей, запись вне репо); десериализация
  недоверенного YAML/pickle; секрет или токен в аудите/сообщении блока/вердикте для inframon;
  исполнение кода из worktree вместо каталога плагина (repo-local подмена скрипта).
- **Claude не может быть ЕДИНСТВЕННЫМ blocking-ревьюером** (сужено 07.08.2026, дизайн
  `docs/2026-08-07-host-relative-reviewer-ladder-design.md` §3). Blocking: панель из одного
  ревьюера семейства, которое могло быть автором, и `auto` со скрытой маршрутизацией — гейт
  превращается в самопроверку, сохраняя вид независимого ревью.
  Claude ДОПУСТИМ внутри обязательной пары Codex+Claude: Claude-авторский код всё равно судит
  Codex, а union не даёт снять чужую находку — ослабить исход присутствие однофамильца не может.
  Прежняя безусловная формулировка «ревьюер обязан быть НЕ-Anthropic» требовала третьего
  семейства и тем делала гейт неработоспособным (0.7.0 не пропускал никого).
- **Подменяемость ревьюера — blocking.** Любой путь, которым вызывающий подставляет свой
  бинарь/команду вместо сертифицированного ревьюера (env-override пути к движку, выбор панели
  переменной окружения, repo-local подмена скрипта), равносилен саморевью.

## Medium/low (совещательно)

Нет теста на новую ветку/except; сообщение об ошибке без контекста; пере-блок безобидного
(fail-safe трение); стиль/нейминг.

При сомнении в severity — меньшую, но опиши риск.

## Scope / известные остатки (НЕ флагать как blocking — осознанные решения)

Реестр спеки `docs/2026-07-22-gates-plugin-port-design.md` (Codex-approved, 4 раунда):

- **AGENTS.md вне жёстких код-путей** — наследованный by-design остаток (циклическая
  зависимость дизайн-гейта); ослабление видно в деплой-диффе; pin — Фаза 2.
- **G1 — session-scoped best-effort, cwd-rooted**: произвольный shell (`cp`/`mv`/
  `python -c`), вложенные репо, checkout до-онбординговой ревизии — вне охвата; дизайн-гейт
  fail-open by design (BS3-асимметрия), денежная защита — fail-closed деплой-цепочка.
- **Version-skew при обновлении плагина посреди коммита** — niche; ledger-tree
  валидируется на деплое.
- **Ladder self-attested**; rebase стирает ledger-покрытие (путь — audited LADDER_SKIP);
  кросс-машинные ledger/baseline локальны.

## Реестр остатков Codex-ревью (scope-решения проекта, НЕ пере-флагать)

- **R-PREPUSH-CONFIG-TRUST — сетевую операцию pre-push надо унести в ГЕЙТ-СОЗДАННЫЙ
  репозиторий (14.08.2026, архитектурное; исключено из сходимости по стоп-политике).**
  Адаптер fetch санирует конфиг проверяемой стороны КЛЮЧ ЗА КЛЮЧОМ: гасит `core.sshCommand`,
  отклоняет `remote.<name>.vcs`, пиннит `--upload-pack`, валидирует URL. Это денилист по чужой
  растущей поверхности, и он не сходится: три раунда дизайн-ревью дали три экземпляра одного
  корня (`GIT_SSH_COMMAND`, `include.path` из рабочего дерева, двухступенчатый `insteadOf`).
  Проверено: `.git/config` тянет `include.path = ../attacker.cfg` из РАБОЧЕГО ДЕРЕВА, а
  `get-url` и `fetch` применяют `insteadOf` независимо — валидируем один URL, тянем другой.
  RCE это не даёт (`ext::` блокируется самим git — проверено), но идентичность базы
  перенаправляется на другой разрешённый URL. Лечение — не ключи, а модель:
  `git init --bare <tmp>` + `GIT_CONFIG_GLOBAL=/dev/null` + `GIT_CONFIG_NOSYSTEM=1`, fetch туда,
  сверка по полученному oid (проверено: работает, конфиг жертвы не читается). Тянет за собой
  перенос `merge-tree`-пробы, которой нужны объекты В РАБОЧЕМ репозитории, — поэтому отдельным
  дизайном. Заодно закроет и закрепление базового URL в `.codex-gate.yaml`.

- **R-TRUSTED-LAYER-DUPLICATION — правило доверия размножено копиями (14.08.2026).**
  Резолв доверенного бинаря живёт в трёх экземплярах (`_trusted_git_bin`, `_trusted_node_bin`,
  `_trusted_ssh_bin`), сборка санированного окружения — в пяти (`codex_review_gate` ×2,
  `prepush_gate` ×2, `ladder_gate`), и дрейф УЖЕ случился: `_trusted_git_bytes` не выставляет
  ни `HOME`, ни `PATH`. Ужесточение правила придётся вносить в каждую копию, а пропуск будет
  тихим. Просится `_trusted_bin(name, extra=())` и `_trusted_env(profile)` в слое, плюс
  `_git_config_args(transport=…)` вместо патчей `_GIT_NEUTRALIZE` на месте у вызывающих
  (сейчас один кортеж патчится двумя несовместимыми матчами — точным сравнением и префиксом).
  Не в хотфиксе: это правка слоя, которым пользуются все три гейта.


- **R-UNSEEN-ASSUME-UNCHANGED — `assume-unchanged` на правленом/удалённом файле делает лесенку
  непроходимой (13.08.2026, воспроизведено на 0.9.0 И на 0.9.1).** `compute_tree` пере-хэширует
  диск и видит правку, `git add -A` её не стейджит — деревья расходятся навсегда, единственный
  выход `LADDER_SKIP`. Это КОНФЛИКТ ДВУХ ИНВАРИАНТОВ, а не недосмотр: паритет с `git add -A`
  требует правку игнорировать, устойчивость к подмене — видеть. Выбран второй (гейт целостности
  обязан видеть спрятанное), цена — неисполнимость в этой конфигурации. Чинить отдельным
  решением: либо диагностика с именем пути вместо немого блока, либо явный отказ на этапе
  `begin`. Не пере-флагать как «баг compute_tree».

- **R-WORKTREE-CLEAN-PARITY — `working_tree_clean` несёт два из четырёх дефектов, вылеченных
  в `ladder_gate` (13.08.2026, воспроизведено).** `codex_review_gate.py:working_tree_clean`
  объявлялась эталоном обработки симлинков, но: в sparse-checkout возвращает `False` ВСЕГДА
  (`if not full.is_file(): return False` на записи вне конуса) — деплой-гейт в таком репо мёртв;
  на не-UTF-8 цели симлинка падает `UnicodeEncodeError` (`os.readlink(full).encode()` вместо
  `os.fsencode`), мимо диагностики, потому что ловится только `OSError`. Плюс недостижимый код
  после `return`. Другой гейт и другой радиус поражения, поэтому в 0.9.1 не трогалось —
  но «лесенка теперь исполнима в sparse-checkout» верно ТОЛЬКО про `ladder_gate.py`.

- **R-TREE-HASH-COST — ЗАКРЫТО в 0.9.4 (14.08.2026).** Было 2N+3 подпроцесса git на дерево:
  12,3 с на 579 файлов на маке против 2,6 с на Linux (замерено телеметрией — разница в цене
  спавна процесса). Стало: пакетный `hash-object --stdin-paths` + один `update-index -z
  --index-info`, **12275 мс → 364 мс (33,7x)** на боевом репозитории. Симлинки остались
  поштучными — см. R-SYMLINK-BATCH.

- **R-SYMLINK-BATCH — симлинки можно батчить, но не в этом релизе (14.08.2026, измерено).**
  `update-index -z --add --stdin` индексирует их пакетом: на репо с 100 симлинками замерено
  106 подпроцессов/1342 мс против 7/120 мс. Не делалось, потому что цена ошибки несоразмерна
  выигрышу: `update-index --add` на ОБЫЧНОМ файле ПРИМЕНЯЕТ clean-фильтр (проверено: `hi` →
  `CORRUPT`), то есть один затесавшийся в этот пакет обычный файл вернул бы ровно ту дыру, от
  которой уходили через `--no-filters`, — молча и на chokepoint'е целостности. В реальных репо
  симлинков единицы (в `wb-ad-ruler` их 8, это ~0,1 с на цикл), так что механизм дороже
  задачи. Если браться — только с отдельной веткой, где структурно невозможно попадание
  не-симлинка, и с тестом на clean-фильтр.


- **R-DEPLOY-PROOF-IS-POINT-IN-TIME — верификация утверждает состояние на момент проверки
  (23.08.2026).** Локальный процесс с правами пользователя может подложить `.pyc` или
  отредактировать `.py` ПОСЛЕ зелёного деплоя — граница одинакова для обоих, и деплой её не
  двигает. Байткод при этом не «детектируется», а СНИМАЕТСЯ: это кэш без полномочий, удаление
  ничего не теряет и делает «что исполнится» равным «что захэшировано»; генерация закрыта
  `python3 -B` в шиме и хуках. Постоянный контроль установки — задача не деплоя.

- **R-GUARD-TEST-MUST-BE-HARMLESS-UNARMED — регресс-тест на разрушительную защиту обязан быть
  безвреден ПРИ СНЯТОЙ защите (24.08.2026, случилось четырежды подряд).** Тест, доказывающий
  страж, полагается на то, что страж не пустит его дальше, — и в тот единственный момент, когда
  страж проверяют мутацией, тест исполняет ровно то разрушение, от которого защищает. Так живой
  плагин сносился трижды и один раз реестр был переписан значениями из тест-фикстуры
  (`installPath=/x, version=666`).

  **Правило:** payload теста обязан быть безобидным сам по себе — заведомо несуществующий путь
  или имя (`/нет/такого/claude`, `НЕСУЩЕСТВУЮЩИЙ-ПЛАГИН`), либо нейтрализованная точка записи
  (подменённый `_atomic_write` + утверждение, что записи НЕ было). Проверка — не рассуждением, а
  мутационным прогоном со снимком боевого состояния до и после: у нас это 10 мутаций, каждая
  обязана и краснеть, и не менять реестр установок и клон маркетплейса.

- **R-TEST-MUTATED-THE-REAL-MACHINE — тест снёс живой плагин (23.08.2026, случилось).**
  `cmd_restore` умеет откатывать «в отсутствие» (снять канал, установленный этим деплоем), и
  адрес мутации брался ИЗ ОКРУЖЕНИЯ (`~`). Тест передал `{"channel": "claude", "state":
  "absent"}` без цели — ветка выполнила `claude plugin uninstall gates@lenar-gates` на рабочей
  машине, запись из `installed_plugins.json` исчезла, шим перестал резолвить гейт. Восстановлено
  `claude plugin install`. **Урок не «быть внимательнее в тестах»:** пока адрес мутации имеет
  умолчание, никакая аккуратность в тестах его не исключает. Закрыто на двух уровнях: (1) цель
  приезжает в спеке явно, неполный спек не мутирует ничего (`no-target`); (2) autouse-страж в
  `conftest` не даёт тесту дотянуться до настоящего CLI.

  **Второй уровень пришлось переделать: денилист написаний провалился четырежды подряд** —
  (1) перехват только `argv[0]` у `subprocess.run` пропускал `Popen`, `check_call`, `shell=` и
  `ssh host "claude plugin …"`, то есть ПРОДАКШН-форму мутации удалённых хостов; (2) запрет
  самого имени `codex` уронил четыре давних теста, потому что это ещё и движок обязательного
  ревью; (3) токенизация всех аргументов ложно срабатывала на тексте промпта, содержащем слова
  «claude plugin»; (4) токенизация «командных позиций» не доставала до `bash -lc`, `env sh -c`
  и, главное, до ВНУКОВ — деплой шлёт агента как `python3 - restore …`, и `claude plugin
  uninstall` зовёт уже он. Разбор argv этот класс закрыть не может в принципе.

  Итог — аллоулист формы: каталог со стабами `claude`/`codex` встаёт первым в `PATH` на импорте
  conftest (не в фикстуре: на этапе сбора фикстур ещё нет) и вклеивается в окружение каждого
  потомка. Формулировка узкая намеренно: настоящий CLI **не резолвится через PATH** — «недостижим
  вообще» было бы переоценкой, потому что боевой код умеет брать абсолютный путь мимо PATH
  (`_resolve_claude_bin`), и от него держит подмена резолверов. Разбор argv оставлен дешёвой
  растяжкой ради внятного сообщения. Явно НЕ покрыто: `bash -lc` (login-профиль пересобирает
  PATH), прямой `subprocess.run(["ssh", host, "claude plugin …"])` из произвольного теста.

  **Третий маршрут — мутация БЕЗ subprocess.** `_installed_claude` читает реестр чистым чтением
  и честно возвращает боевой адрес; `cmd_restore` затем в него пишет, а `cmd_verify` идёт
  `rmtree`'ом по `__pycache__` живой установки. Ни PATH, ни argv, ни транспорт тут не
  участвуют, а проверка «адрес не боевой» в самом `cmd_restore` была бы неверна: на хосте
  писать в боевой реестр — это его работа. Chokepoint поставлен со стороны тестов: результат
  `installed()` и спек `cmd_restore` отвергаются, если адрес лежит под настоящим `~`. Туда же
  инертные `deploy_gates.on_host`, `_drop_mux`, `STATE`/`LOCK`. Каждый слой краснеет при снятии
  другого.

  **Второй инцидент — регресс-тест был живобоевым.** Проверяя регрессию стража, ревьюер
  запустил `Popen(["claude","plugin","uninstall","gates@lenar-gates"])`, и тест исполнил
  разрушительную команду по-настоящему: он воспроизводил инцидент вместо того, чтобы его
  обнаруживать. Теперь путь заведомо несуществующий — растяжка ловит по basename, а без неё
  будет `FileNotFoundError`, а не мутация.

- **R-DEPLOY-SMOKE-STATE-LEAK — smoke оставляет каталог состояния гейта (23.08.2026,
  замерено).** Запуск лесенки во временном репозитории создаёт каталог в
  `~/.local/state/claude-gates/<ключ>`; один прогон тестов давал 4 новых. Смягчено: smoke
  спрашивает адрес у САМОГО кода и убирает за собой. Не устранено структурно — правило ключа
  живёт в гейте, а `_gate_state_dir` намеренно игнорирует `XDG_STATE_HOME` (иначе состояние
  гейта переехало бы в каталог проверяемой стороны). Остаточный риск: при падении smoke до
  `finally` каталог останется.

- **R-DEPLOY-STATUS-IS-A-RECORD — `--status` не опрашивает флот (23.08.2026).** Печатает
  запись последней сертификации, а не текущее состояние хостов; так и подписано в выводе.
  Опрос — это полный `verify` по всем хостам, то есть `make deploy` без мутации; отдельный
  режим не строился, потому что честный ответ «проверь заново» дешевле второго маршрута
  проверки, который может разойтись с основным.

- **R-DEPLOY-DESIGN-DRIFT — три обещания дизайна не реализованы (23.08.2026).** §Р1.4 «версия
  отличается от уже задеплоенной хотя бы на одном хосте» — нет: деплой идемпотентен, повторный
  прогон просто подтверждает состояние, и отдельная проверка «нечего делать» дала бы ещё один
  путь, где «ничего не сделано» неотличимо от «всё сошлось». §Р4 `make gates-restore
  HOST=… VERSION=…` — параметра `VERSION` нет, откат идёт по снапшоту (единственная цель,
  которую деплой умеет ДОКАЗАТЬ). §Р4 называет путь состояния `.deploy-state/`, фактически оно
  живёт рядом с состоянием гейта вне репозитория — код строже дизайна.

- **R-DEPLOY-FETCH-REUSES-PREPUSH-ADAPTER — сетевой путь деплоя один, и он чужой
  (24.08.2026).** `_trusted_git` для `fetch` непригоден по построению: слой намеренно глушит
  сеть (`protocol.allow=never`), и выкатка падала с `transport 'ssh' not allowed` — причём
  собственное сообщение драйвера причины не несло, её пришлось доставать руками. Драйвер зовёт
  `prepush_gate._prepush_fetch`: закреплённые бинарь git и ssh, аллоулист окружения, валидация
  URL против `ext::`, разрешение РОВНО схемы провалидированного URL, отклонение
  `remote.<name>.vcs`/`uploadpack`, нейтральный cwd. Своя копия этих правил стала бы третьей и
  разъехалась бы первой (ср. R-TRUSTED-LAYER-DUPLICATION). Цена: деплой зависит от модуля
  pre-push гейта; при его переработке сетевой путь выкатки надо проверять вместе с ним.

- **R-DEPLOY-NO-RESUME-JOURNAL — прерванный деплой не возобновляется, повторяется (23.08.2026).**
  Обрыв процесса посреди выкатки оставляет снапшоты на диске; лечится повторным `make deploy`
  (идемпотентен) или `make gates-restore HOST=…`. Журнал прогресса окупается на десятке хостов,
  а во флоте их два — механизм дороже задачи. Пересмотреть, когда хостов станет больше трёх.

- **R-DEPLOY-INSTALL-FROM-MUTABLE-MAIN — ставим из изменяемого `origin/main`, не из
  артефакта (23.08.2026).** Правильное решение — собрать артефакт с дайджестом и доставить его,
  но CLI обоих каналов такого не умеет, а собственный канал доставки — это ВТОРОЙ способ ставить
  плагин, то есть новая поверхность отказа взамен обнаруживаемой гонки. Вместо этого гонка
  закрыта наблюдением: sha закрепляется один раз до выкатки, и верификация на каждом хосте
  сверяет установленный sha и дайджест дерева с закреплённым. Разъезд не предотвращён, но
  не может пройти молча.

- **R-DEPLOY-LOCK-IS-NOT-A-LEASE — замок деплоя без владельца и срока (23.08.2026).**
  `.deploy-state/lock` (pid + sha) падает громко при конкурентном запуске, но это не аренда:
  залипший файл после SIGKILL снимается руками, и на самих хостах замка нет вовсе. Закрывает
  наблюдавшийся сценарий (два прогона с разными sha чередуются и дают зелёный результат на
  расколотом флоте); распределённая аренда — механизм для флота, которого нет. `stable` хранит
  sha, поэтому раскол обнаружим постфактум.

- **R-BUDGET-CONCURRENCY — две сессии могут превысить бюджет ревью на раунд (11.08.2026,
  находка отклонена сознательно).** `check` и `increment` разделены внешним вызовом ревью,
  поэтому при одном оставшемся слоте две параллельные сессии обе стартуют. Цена ошибки —
  ОДИН лишний оплаченный раунд ревью, то есть больше проверки, а не меньше; деплой от бюджета
  не зависит вовсе. Предложенная дешёвая правка (держать artifact-lock весь внешний вызов)
  вводит замок на 15 минут поверх сетевой операции — риск залипания и блокировки чужой работы
  превышает предотвращаемую потерю. **Первое применение стоп-политики v3 в обратную сторону:**
  не каждую находку надо чинить. Дизайн: `docs/methodology/2026-08-11-review-budget-design.md`.

- **R-DESIGN-FINDINGS-LEDGER — находки дизайн-ревью нигде не сохраняются (11.08.2026).**
  Поэтому дизайн-артефакты выведены из-под бюджета и `residuals-accept` ЦЕЛИКОМ: обещать
  «блокирующие дизайн-находки под особым правилом» было бы неисполнимо — блокировать нечему.
  «Один раунд по подходу» остаётся правилом скилла, а не механикой. Полное решение —
  структурный вывод дизайн-ревью, отдельный ledger по хэшу файла и запрет `write-marker` при
  открытых блокирующих находках — не построено: заметный механизм ради случая, который
  закрывается запретом.

- **R-CATEGORY-CONTRACT — категория находки и пересертификация НЕ реализованы (11.08.2026,
  решение по бюджету ревью).** Ярус предложений арбитра требует категории находки, а контракт
  ревьюера её не выдаёт, поэтому работает только арбитрация дубликатов. Полный разбор — в
  `docs/2026-08-10-reviewer-category-contract-design.md` (ред. 15, 14 раундов ревью): там
  перечислены все найденные мины, включая нереализуемую сертификацию арбитра, JSON-first
  разбор Codex, чужую схему companion'а как невыполнимую зависимость, потерю категории при
  слиянии находок и гонки read-decide-commit.
  **Почему не реализовано:** радиус поражения фичи — «оператор увидит готовый аргумент за
  снятие находки», а требуемый механизм (HMAC-обязательства улик, CAS с digest входа,
  счётчики поколений, перестройка корпуса втрое, живые прогоны трёх моделей) несопоставим с
  этой ценностью. Решение по стоп-политике v3: ярус `convenience`, бюджет исчерпан, остаток
  принят. Возвращаться — только если появится независимая причина менять контракт ревьюера.

- **R-BASELINE-ADAPTER — форма `deploy.baseline_command` закрыта (09.08.2026, 10 раундов security).**
  Принимается РОВНО один абсолютный путь к исполняемому файлу вне репозитория, без аргументов;
  запуск с `cwd=/`, `stdin=DEVNULL` и аллоулистом окружения. Свободная команда непроверяема:
  четыре раунда подряд обходили лексические проверки — `./ops/sha`, `/bin/sh ops/sha`,
  `sh -c 'cd "$HOME"; cd src; …'` (ни одного путеподобного аргумента) и, наконец, `/bin/sh`
  без аргументов, читающий stdin, плюс `TMPDIR` внутрь репозитория для инструментов, ищущих
  конфиг вверх по дереву. **Fail-safe цена:** адаптеру, которому нужен рабочий cwd,
  TMPDIR, stdin или поиск конфига вверх по дереву, гейт откажет — деплой встанет. Песочницы
  ФС тут НЕТ: `cwd=/` лишает адаптер репозиторного контекста, но относительная запись в
  доступный на запись каталог по-прежнему возможна правами пользователя.
  Логику надо оборачивать в самодостаточный скрипт ВНЕ проверяемого дерева.

- **R-EVIDENCE-SELFSIGNED — состояние гейта не подписано (09.08.2026).**
  `review-baseline`, `panel-evidence.json` и `deploy-section-pin` вынесены из репозитория в
  `~/.local/state/claude-gates/<ключ>` (HOME — из БД пользователей, не из окружения; если
  каталог оказался бы внутри репозитория — fail-closed). Их по-прежнему может переписать тот
  же пользователь: это прежняя граница «владелец машины — доверенная сторона».
  Неподделываемость требует внешнего подписывающего сервиса — Фаза 2.

- **R-BINARY-REVIEW — бинарь блокирует деплой (09.08.2026).**
  Содержимое бинарного/не-UTF-8 blob'а ревьюеры увидеть не могут (во вход идут размер и
  sha256), а в артефакт он уезжает целиком. Одобрение непрозрачного хэша больше не считается
  ревью: диапазон с бинарным изменением блокирует деплой. Обход `GATES_ALLOW_BINARY=1`
  аудируется и **не оставляет evidence** — baseline не двигается, диапазон остаётся в области
  следующего ревью. **Fail-safe цена:** проект, выкатывающий бинарные ассеты, обязан явно
  включать обход каждый раз.

- **R-PROBE-SMUDGE — интеграционный probe несовместим с обычным Git LFS (09.08.2026).**
  `worktree add` делает checkout и исполняет `smudge`/`process`-фильтры, ВЫБРАННЫЕ атрибутами
  проверяемого репозитория; имя драйвера произвольно, поэтому гасить поимённо нельзя, а
  доверять по имени — тот же денилист, который здесь уже дважды провалился. Probe падает
  закрыто при любом настроенном smudge/process. `clean`-only конфигурации checkout не
  исполняет, они работают как раньше. Обычный LFS настраивает smudge+process — такому проекту
  интеграционный probe придётся выключить осознанно (аудируется). Полное решение —
  материализация probe без checkout, Фаза 2. Дизайн: `docs/2026-08-08-trusted-git-layer-design.md` §5.2.

- **R-ACTUATOR-HANDOFF (уточнён 09.08.2026) — гейт не знает, что стоит в проде.**
  Попытка доказать факт выкатки квитанцией отвергнута ревью: квитанция состоит из величин,
  уже известных рецепту, и им же воспроизводится. Вывод — не усиливать квитанцию, а убрать
  зависимость: baseline РЕВЬЮ больше не читает `.last-deployed-sha` (его писал рецепт —
  недоверенная сторона) и двигается гейтом только при evidence КАЖДОГО обязательного
  блокирующего ревьюера по этому head. Аварийный `CODEX_REVIEW_SKIP` evidence не оставляет,
  поэтому пропущенный диапазон остаётся в области следующего ревью. Что НЕ гарантируется:
  что выкачено именно то и вообще выкачено. Потеря покрытия ревью закрыта, знание о проде — нет.

- **R-ARBITER-FAMILY / R-ARBITER-COVERAGE (09.08.2026) — арбитр-третья-модель.**
  Реализован: подкоманда `arbitrate`, роль `arbiter` в реестре, статус `resolved-by-arbiter`,
  инвариант графа дубликатов. **Пока НЕ активен:** запись Fable — `candidate`, а роль требует
  `verified`, поэтому арбитр не вызывается и гейт ведёт себя как до фичи (fail-closed).
  Активируется прогоном сертификации на арбитражном корпусе.
  ⚠️ **Ярус предложений в проде пока НЕДОСТИЖИМ:** он требует распознанной категории
  находки, а контракт ревьюера её не выдаёт (только severity и заголовок), и `merge_round`
  её не пишет. То есть фактически реализована ТОЛЬКО арбитрация дубликатов; всё остальное
  идёт человеку, как и раньше. Расширение контракта ревьюера — отдельное изменение с
  ПЕРЕсертификацией (корпус проверяет разбор ответа), поэтому оно не сделано заодно.
  Границы: терминален ровно один класс (`duplicate` с сохраняемым инвариантом графа под
  series-lock); всё остальное — ПРЕДЛОЖЕНИЕ, которое принимает ЧЕЛОВЕК командой
  `adjudicate <F> resolved-by-arbiter --operator-confirmed`. Подтверждение ревьюером
  отвергнуто: его ответ порождён недоверенным диффом, и инъекция в нём может навязать
  подтверждение — авторизация, переносимая таким каналом, не авторизация.
  **Fail-safe цена:** большая часть тупиков по-прежнему доходит до человека, но с уже
  написанным разбором — от него нужно решение, а не расследование.

- **R-STATE-OUT-OF-REPO (09.08.2026) — всё состояние решений вне репозитория.**
  `review_findings`, `review_ledger`, `review-baseline`, `panel-evidence`, `deploy-section-pin`
  живут в `~/.local/state/claude-gates/<ключ>`. Раньше первые два лежали в игнорируемом
  `logs/`: проверка чистоты дерева их не видела, и проверяемая сторона писала кэш ревью,
  фактическую панель и записи арбитра — evidence собственной невиновности. Оверрайды
  `CODEX_*_DIR` теперь отвергают путь, чей лексический путь ИЛИ цель симлинка внутри
  репозитория, и возвращают канонический путь. Проверка вложенности — по идентичности ФС
  (`samefile`), а не по тексту: на регистронезависимой ФС путь в другом регистре её обходил.
  Verified не-anthropic арбитра на машине оператора нет, поэтому однофамильный арбитр не может
  терминально снять блокирующую находку единственного не-anthropic члена панели — его вердикт
  становится предложением автору находки. Терминален ровно один класс (`duplicate` с
  сохраняемым инвариантом графа), поэтому большая часть тупиков по-прежнему уходит человеку:
  расширять аллоулист можно только доказав fail-safe нового класса, а не тем, что «в нём
  обычно нет денег». Дизайн: `docs/2026-08-09-arbiter-third-model-design.md`.

- **M8 — `declared`-аттестация Codex (07.08.2026, решение владельца продукта, 5 раундов ревью).**
  Codex companion возвращает `model: request.model` (эхо запроса), а `codex_model()` читает
  локальный `~/.codex/config.toml` — фактическая модель НЕ аттестуется. Ревью настаивало, что
  такая запись не может занимать слот независимости в обязательной паре: при скрытой
  маршрутизации на Anthropic-модель оба слота окажутся одного семейства. Возражение логически
  верно и ОТКЛОНЕНО сознательно: альтернатива — deploy-гейт, не работающий ни в одной доступной
  конфигурации (единственный `verified` независимый ревьюер, Gemini, требует стороннего ключа,
  который продукт не делает обязательным). Границы отступления: `declared` допускается только
  для адаптера, запускающего локальный бинарь/плагин под контролем пользователя, только при
  наличии второго `verified`-члена панели, и никогда как единственный член. Снимается
  автоматически, как только companion начнёт отдавать фактическую модель. Дизайн:
  `docs/2026-08-07-host-relative-reviewer-ladder-design.md` §6.

- **Служебная модель того же вендора в `modelUsage` (08.08.2026, уточнение S10).**
  Правило «фактическая модель обязана совпасть с реестром» требовало РОВНО ОДНОЙ модели в
  ответе. Замер 08.08.2026 под обязательным `--safe-mode`: Claude CLI стабильно привлекает
  служебную `claude-haiku-4-5` (вход 5893 / выход ~15) рядом с `claude-opus-5` (выход ~250),
  который и пишет вердикт. Прежнее правило отвергало бы КОРРЕКТНЫЕ ревью. Уточнено: в ответе
  обязана присутствовать сертифицированная модель, она обязана дать НАИБОЛЬШИЙ выход (то есть
  написать вердикт), а любая другая модель — принадлежать тому же семейству. Модель чужого
  вендора и сертифицированная модель, не писавшая ответ, по-прежнему делают артефакт
  невалидным, поэтому исходный смысл S10 (скрытая маршрутизация → блок) сохранён.
  Список служебных моделей НЕ фиксируется по именам: они меняются с версиями CLI, и жёсткий
  список ломался бы при каждом обновлении.

- **R-VERDICT-PROVENANCE — атрибуция модели по токенам не доказывает авторство (08.08.2026 → Фаза 2).**
  `modelUsage` и `result` — независимые поля конверта; связи «этот текст написала эта модель»
  в ответе нет. Гейт требует, чтобы сертифицированная модель присутствовала, имела СТРОГО
  наибольший положительный выход и чтобы все прочие модели были того же семейства (ничьи и
  отсутствующие счётчики теперь отвергаются — раньше `0 == max(0,0)` пропускал артефакт без
  всякой атрибуции). Это эвристика: подмена ВНУТРИ семейства с подходящим распределением
  токенов её пройдёт. Что она гарантирует: чужой вендор отвергается, то есть НЕЗАВИСИМОСТЬ
  панели (не-anthropic ревьюер для anthropic-авторского кода) обеспечивается Codex'ом и от
  этой эвристики не зависит; под риском остаётся КАЧЕСТВО ревью, если CLI подставит более
  слабую модель того же вендора. Настоящее закрытие — per-message provenance (stream-json,
  где терминальное assistant-сообщение несёт имя модели) с fail-closed при отсутствии связи.

- **R-HUMAN-APPROVAL — `resolved-by-user` не доказывает участие человека (08.08.2026 → Фаза 2).**
  Эта адъюдикация мгновенно снимает блокирующую находку и вызывается через тот же CLI, что и
  остальные, то есть доступна агенту, который пишет код. Требование интерактивного терминала
  отсекает дефолтный неинтерактивный вызов, но доказательством не является: агент может
  выделить PTY (проверено ревью 08.08.2026). Механически отличить агента от человека на одной
  машине нельзя — нужен внеполосный подписанный одноразовый артефакт, привязанный к репозиторию,
  baseline, id находки и решению.
  **Требование TTY отменено 09.08.2026 по боевому опыту:** под Claude Code даже `!`-команда идёт
  без tty, поэтому оператору приходилось открывать отдельный терминал — препятствие не держало
  нарушителя, но выгоняло добросовестного из рабочего окружения. Взамен — явное
  `--operator-confirmed`: оно тоже ничего не доказывает, но снимает случайность и попадает в
  аудит меткой `HUMAN-APPROVAL … via=…`. Защита держится на ГРОМКОСТИ: каждое такое решение
  видно постфактум. Практическое следствие: эскалация к человеку — организационный контроль,
  а не технический.

- **R-ARTIFACT-PROVENANCE — подмена БИНАРЯ ревьюера в собственном HOME (07.08.2026 → Фаза 2).**
  Гейт исполняется от имени того же пользователя, чей домашний каталог содержит и `claude`
  (`~/.local/bin`, `~/.claude/local`, `~/.volta`, `~/.nvm`), и companion-плагин. Эти артефакты
  caller-writable по определению, поэтому вызывающий может подменить любой из них шимом,
  печатающим `Verdict: approve` с ожидаемым `modelUsage` — проверка фактической модели тогда
  выполняется НАД ДАННЫМИ ШИМА. Закрыто всё, что закрывается кодом гейта: переменные окружения
  (аллоулист из 8 значений), путь к движку (доверенный HOME из БД пользователей, абсолютный
  `node`, запрет repo-local), маршрут через конфиг (стерильный gate-owned `CODEX_HOME` только
  с моделью). НЕ закрывается и не может быть закрыто патчем гейта: доверие к самим артефактам —
  нужны immutable/system-owned установки либо проверка подписи/дайджеста до запуска, что ломает
  обычное обновление CLI. Это та же семья, что R-CERT-PROVENANCE: без доверенной инфраструктуры
  исполнения «операторская учётка враждебна» не моделируется. Практическая граница: гейт
  защищает от СЛУЧАЙНОГО обхода и заставляет любое изменение gated-кода пройти ревью, но НЕ
  является техническим барьером против того, кто владеет машиной, — включая агента,
  исполняющегося с её правами (см. R-HUMAN-APPROVAL: снять находку через `resolved-by-user`
  агент технически может). Ценность гейта здесь — принуждение к процессу и следы в аудите,
  а не невозможность обхода.

- **R-CERT-PROVENANCE — подделка отчёта сертификации вместе с реестром (07.08.2026 → Фаза 2).**
  Связка отчёта с реестром (path, sha256, corpus digest, provider/adapter/model/role/
  certification_id, полная матрица кейс×повтор, единственная фактическая модель во всех строках,
  путь внутри поставляемого каталога) доказывает согласованность двух коммитабельных артефактов,
  но не доверенное исполнение: автор может написать отчёт с `pass: true`, посчитать sha и
  поправить реестр одним коммитом. Полное закрытие требует подписи CI над отчётом, digest'ом
  корпуса, digest'ом кода адаптера и идентичностью реестра с проверкой подписанта — отдельная
  инфраструктура, Фаза 2. До неё защита: реестр сертификаций — код-путь в `.codex-gate.yaml`,
  то есть его правка сама проходит deploy-гейт и независимого ревьюера. Дизайн: §7.

- **Редакция секретов — defense-in-depth по ОБРАЗЦАМ, не гарантия (25.07, 7 раундов ревью).**
  `redact_secrets` закрывает распознаваемые формы: помеченные пары `KEY=value` (в т.ч. ключ как
  часть идентификатора вроде `AWS_SECRET_ACCESS_KEY`), схемы аутентификации (Bearer/Basic/Digest
  + поля `response/nonce/cnonce/opaque`), префиксы провайдеров (sk-/ghp_/github_pat_/xox*/AKIA/
  ASIA), JWT, подписи в URL, DSN-креды (в т.ч. без имени пользователя), длинный неразрывный
  токен ≥40. Применяется у ВСЕХ 8 источников недоверенного текста (реестр в коде
  `codex_review_gate.py` рядом с `redact_secrets`).
  **НЕ ловится по построению (осознанный остаток, НЕ флагать как blocking):** значение без
  распознаваемой формы и без метки (произвольная проза, короткие/низкоэнтропийные значения ниже
  порогов), а также секрет, который оператор проносит намеренно. Хэши/SHA и пути конфигов НЕ
  редактируются намеренно (64-hex попал бы под правило длинного токена и сломал бы маркер).
  Новый ИСТОЧНИК недоверенного текста → редактировать в его источнике и дописать в реестр;
  новая ФОРМА секрета → правило добавлять, только если это широко стандартный формат.

- **empirical ML-E5 (2026-07-22, residual-failsafe → Фаза 2):** env-ослабление неизменной
  тест-команды (`PATH=/tmp/shims make deploy` подменяет `pytest` шимом; `PYTEST_ADDOPTS` и т.п.).
  НЕ чиним: тест-раннеру environment нужен (санитизация = fail-safe пере-блок), а оператор,
  задающий env на деплой, эквивалентен задающему `EMPIRICAL_SKIP` — защита от злонамеренного
  оператора вне охвата Фазы 1. Герметичный прогон в изолированном образе из отревьюенного
  коммита — Фаза 2 (тот же immutable-artifact-биндинг, что закрывает reviewed≡deployed). Порог
  эмпирического гейта: «поймать сломанные тесты + сделать конфиг-обходы аудируемыми», НЕ
  «остановить оператора с доступом к деплой-машине». Спека: docs/2026-07-22-empirical-gate-design.md ML-E5.
