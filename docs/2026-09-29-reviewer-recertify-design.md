# Перекалибровка Claude-ревьюера без простоя: закреплённая модель + `make recertify`

Дата: 2026-09-29. Ярус: `decision` (влияет на вердикт гейта).

## Проблема (воспроизведено 29.09.2026)

Гейт запрашивал Claude-ревьюера АЛИАСОМ `opus` (`_CLAUDE_REQUESTED_MODEL`), а реестр
сертифицирует ТОЧНУЮ модель. Вендор перевёл алиас на `claude-opus-5-5` → фактическая модель
разошлась с `claude-opus-5` → Claude-слот обязательной пары отвергнут → деплой-гейт закрыт у
всех пользователей плагина до ручной перекалибровки. Fail-closed сработал верно, но:

1. **Простой не нужен:** старая сертифицированная модель продолжала существовать и работать —
   гейт отказался от неё только потому, что спрашивал алиасом.
2. **Диагностика немая:** «модель не совпала с реестром» без имени увиденной и ожидаемой модели.
3. **Перекалибровка ручная:** правка реестра, прогон, sha, версия — пять шагов, каждый
   с шансом ошибки (первый же прогон показал: без поднятия версии CLI не доставит реестр).

## Решение

### Р1. Запрашиваемая модель берётся из реестра, а не из кода

`claude_blocking_model()` возвращает `requested_model` ЕДИНСТВЕННОЙ записи
`provider=claude, role=blocking` (certified; с `allow_candidate` — любой статус). Ноль или
больше одного различного значения → `None` → обязательная пара неполна → fail-closed с
сообщением. Константа `_CLAUDE_REQUESTED_MODEL` удаляется. В реестре `requested_model`
становится точным id (`claude-opus-5-5`), равным `actual_models[0]`.

Смена алиаса у вендора больше гейт не останавливает. Снятие закреплённой модели с поддержки
остановит (CLI вернёт ошибку → `invalid` → fail-closed) — это правильно и лечится Р3.

**Не ослабление:** источник по-прежнему только поставляемый реестр (код-путь, ревьюится
деплой-гейтом); ни конфиг проекта, ни окружение модель не выбирают. Проверка фактической модели
(`modelUsage`) не меняется.

### Р2. Диагностика расхождения называет модели

Сообщение `invalid` при несовпадении фактической модели несёт увиденные модели (уже
редактированные `redact_secrets`) и сертифицированную, плюс указание: «перекалибровка —
`make recertify` в репозитории плагина».

### Р3. `make recertify` (скрипт `scripts/recertify.py`, не поставляется на хосты)

1. Проба: `claude -p --model opus --output-format json` → единственная модель наибольшего
   выхода из `modelUsage`. Имя валидируется `claude-[a-z0-9.-]+` (оно станет частью
   certification_id и пути отчёта) и семейством `anthropic`. Иначе — отказ, ничего не меняется.
   `--model <id>` задаёт цель явно, минуя пробу.
2. «Актуально» определяется ТЕМ ЖЕ валидированным путём, что и в проде:
   `reviewer_certification("claude", цель, "blocking")` не `None` (то есть связка отчёта,
   digest корпуса и матрица сошлись) И `claude_blocking_model() == цель`. Только тогда выход 0.
   Запись, объявленная certified, но пониженная загрузчиком (отчёт пропал/битый, корпус
   изменился, прерванная прошлая перекалибровка), — НЕ актуальна: прогон идёт заново.
3. Замок: `fcntl.flock` на файле в git-каталоге репозитория (`<git-dir>/gates-recertify.lock`),
   неблокирующий — второй запуск отказывает сразу (выход 2). SIGTERM переводится в исключение,
   чтобы откат в `finally` отработал.
4. Транзакция по ВСЕМ затрагиваемым файлам. До первой мутации — снимок байтов: реестр, четыре
   манифеста, CHANGELOG, старый отчёт (если есть). Порядок мутаций:
   a. реестр: запись Claude-blocking → candidate-запись цели (`<модель>-blocking-<YYYYMMDD>`,
      дата UTC); прогон `certify_reviewers.run_provider("claude")`;
   b. провал корпуса → откат, отчёт провала — в каталог состояния (НЕ в `reports/`), выход 2;
   c. успех → новый отчёт атомарно (tmp + `os.replace`) в `reports/`; манифесты и CHANGELOG;
      реестр → certified со связкой — ПОСЛЕДНЕЙ записью в реестр; старый отчёт удаляется
      самым последним шагом и только если его путь отличается от нового.
   Любое исключение на любом шаге → все файлы снимка восстанавливаются побайтово, новый отчёт
   (если его не было в снимке) удаляется. Итог: либо полный новый набор, либо побайтово прежний.
5. Коммит, лесенка, PR и мерж — как у любой правки: скрипт их НЕ делает (повышение статуса
   остаётся ревьюируемой правкой — инвариант `certify_reviewers.py`).

## Сценарии и приёмочные критерии (BSAC)

Топ-уровневые сценарии:

- **S1. Вендор сдвинул алиас.** Гейт продолжает ревьюить закреплённой моделью; ревью проходит.
  Проверка: тест — реестр с `claude-x-1`, CLI-стаб получает `--model claude-x-1`.
- **S2. Перекалибровка на новую модель.** `make recertify` → реестр/отчёт/версия изменены,
  полный набор тестов зелёный. Проверка: тест на tmp-копии; живой прогон на этой ветке.
- **S3. Новая модель проваливает корпус.** Реестр и манифесты побайтово прежние, отчёт провала
  вне `reports/`, выход 2. Проверка: тест.
- **S4. Модель уже актуальна** (эффективно, через валидацию связки). Выход 0, ни одного
  изменения файлов. Проверка: тест.
- **S4b. Запись объявлена certified, но недействительна** (нет отчёта / битый sha / новый
  корпус). Идёт полный прогон, а не «актуально». Проверка: тест на каждый из трёх видов.
- **S6. Второй одновременный запуск** → отказ с выходом 2, файлы первого не тронуты. Тест.
- **S5. Закреплённую модель сняли с поддержки / фактическая модель разошлась.** Fail-closed,
  сообщение называет обе модели и `make recertify`. Проверка: тест на текст.

Краевые случаи, где гейт мог бы пропустить непроверенное (fail-open), и защита:

- **E1. Две Claude-blocking записи с разными моделями** (недоделанная перекалибровка) — выбор
  «первой» сделал бы порядок JSON решающим. → `None`, fail-closed. Тест.
- **E2. Записи нет / только candidate в проде** → `None`, fail-closed. Тест.
- **E3. Проба вернула чужое семейство, мусор, путь (`../x`), несколько моделей без
  единственного максимума** → отказ до любой записи. Тест.
- **E4. Прерывание на любом шаге** (исключение раннера, сбой записи манифеста, отчёта,
  реестра; SIGINT/SIGTERM) → ВСЕ файлы снимка побайтово прежние, нового отчёта нет.
  Fault-injection тест после каждой точки мутации. SIGKILL отката не даёт: рабочее дерево
  может остаться с candidate-записью или частичным набором — гейт на нём fail-closed
  (candidate слота не даёт, связка не сойдётся), `git diff` это показывает, повторный
  `make recertify` не признает такое состояние актуальным (S4b) и доведёт прогон.
- **E5. Скрипт подменил запись, но тесты/ревью не видели** → невозможно: результат —
  незакоммиченная правка код-пути, которую проходит лесенка и деплой-гейт.
- **E6. Тест recertify пишет в боевой реестр** → все тесты работают на tmp-копиях через
  monkeypatch путей; отдельный тест-страж сверяет sha боевого реестра до и после.

Вне охвата: автоматический запуск по расписанию (локальный cron/launchd — настройка машины,
мониторинг — зона inframon); Codex (модель задаётся `~/.codex/config.toml`, M8); арбитр
`fable` (роль не активна).
