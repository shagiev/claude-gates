# Дизайн: tree-хэш лесенки на нерегулярных записях + громкий сигнал «движок сломан» (0.9.1)

Инцидент: `BUG-0.9.0-symlink-tree-hash.md`. Severity critical — в репозитории с
tracked-симлинком на директорию лесенка неисполнима, единственный путь коммита — `LADDER_SKIP=1`.

**Ревизия 2 (после дизайн-ревью Codex, 2026-08-13).** Ревью нашло две вещи, обе
воспроизведены и подтверждены; обе приняты:

- **critical** — подмодули: заявленный «вне scope, тихая дыра» на самом деле ВТОРОЙ полный
  отказ лесенки, той же тяжести, что симлинки. Мой разбор M4 был неверен (см. §1 П3).
- **high** — `text=True` не переносит цель симлинка с не-UTF-8 байтом: `UnicodeEncodeError`,
  причём мимо нового громкого диагноза (это не `TrustedGitError`).

## 1. Задача

Три проблемы одного корня, все подтверждены воспроизведением на текущем `main` (f5a81c2).
Корень общий: `compute_tree` считает, что запись дерева — это **регулярный файл, хэшируемый
по пути**. Всё, что git умеет, а эта модель — нет (симлинк, gitlink, сырые байты), даёт либо
падение, либо неверный хэш.

### П1. `compute_tree` неверно получает блоб симлинка

`plugins/gates/scripts/ladder_gate.py:215-223`: режим для симлинка определяется верно
(`120000`), но блоб берётся `git hash-object --no-filters -w -- <rel>` **по пути**, а
`hash-object` разыменовывает ссылку.

Проверено (`/tmp/.../repro`, git 2.x):

| случай | сегодня | правильно |
|---|---|---|
| симлинк → директория | `fatal: Unable to add (null) to database`, exit 128 → `TrustedGitError` → **лесенка неисполнима** | блоб = текст цели |
| симлинк → файл | молча хэширует **содержимое цели** (`587be6b4…`) вместо текста ссылки (`33dfaa4e…`) → tree-хэш ≠ git-ову, **тихо** | блоб = текст цели |
| битый симлинк | `hash-object` падает → лесенка неисполнима | блоб = текст цели |

То есть П1 — не только отказ доступности, но и тихая неверность хэша, который является
chokepoint'ом целостности лесенки («код, который отревьюен = код, который коммитится»).

0.8.0 не падал, потому что ветки `is_symlink()` не было: `Path.is_file()` на
симлинке-на-директорию ложно → `continue`, симлинки просто выпадали из хэша (тихая дыра,
но fail-safe по доступности). 0.9.0 честно попытался их учесть и превратил тихий пропуск в
жёсткое падение — цена ошибки выросла с «дыра» до «гейт выключен».

**Эталон уже есть в этом же кодовом дереве:** `working_tree_clean`
(`codex_review_gate.py:958-966`) для `mode == "120000"` берёт `os.readlink()` и считает
sha1 от `blob <len>\0<target>`. `compute_tree` — единственное место, которое расходится с
этим эталоном. Других мест, хэширующих рабочее дерево, в плагине нет
(`grep -rn hash-object plugins/` → ровно эти два).

Дополнительно: цель симлинка может содержать **любые байты кроме NUL** (POSIX), а
`os.readlink()` отдаёт `str` с surrogate-escape. `_git_mutate` работает в `text=True`
(строгое кодирование), поэтому такая цель даёт `UnicodeEncodeError` — не `TrustedGitError`,
то есть трейсбек мимо всей диагностики. Воспроизведено:
`os.symlink(b"real/\xff\xfename", …)` → `compute_tree` падает `UnicodeEncodeError`.

### П3. Подмодуль (mode 160000) выпадает из дерева — ВТОРОЙ полный отказ лесенки

`ls-files -c` отдаёт gitlink, но `is_symlink()`/`is_file()` на нём ложны → `continue`.
Я оценил это как тихую дыру («бамп подмодуля невидим, гейт зелёный»). **Это неверно**, и
ревью право. `check_precommit` сверяет `tree_after` последнего маркера с
`index_tree(root)` — деревом РЕАЛЬНОГО индекса, а в нём gitlink есть всегда. Значит
`compute_tree` (без gitlink'а) не может совпасть с `index_tree` (с gitlink'ом) **никогда**,
даже когда указатель не двигался.

Воспроизведено на движке (репо `top` с подмодулем `sub`, честно пройдены ВСЕ три прохода):

```
compute_tree : 9d9cebb1d8ed2c505f24878c98d4ebeac2359a8a   (нет записи sub)
index_tree   : 93c6722a58e3fe57c6b2866aae923627826ab51f   (= git HEAD tree, sub есть)
check_precommit после полной честной цепочки → 2
```

То есть в любом репозитории с подмодулем лесенка так же неисполнима, как в репозитории с
симлинком на директорию, и так же выталкивает оператора на `LADDER_SKIP=1`. Это не «остаток»,
а тот же инцидент другой формы — поэтому подмодули **входят в scope**.

### П2. Отказ движка неотличим от «проходы не отмечены»

Когда `compute_tree` падает, `begin`/`mark` умирают трейсбеком, маркеров нет, и
`check_precommit` печатает **штатное** «цепочка … не подтверждена» с подсказкой
`LADDER_SKIP=1` в конце. Оператор видит ровно то же, что при собственной забывчивости, и
подсказка ведёт прямо к обходу гейта. Так поломка прожила двое суток незамеченной.

Дополнительно текст `не посчитать хэш X` не несёт stderr от git — причина не диагностируется
без ручного воспроизведения `hash-object`.

### П4. Отсутствие в рабочем дереве ≠ удаление (sparse checkout / SKIP_WORKTREE)

Найдено раундом 2 ревью, воспроизведено — и оказалось **шире**, чем сформулировало ревью.
Ветка `else: continue` трактует «пути нет на диске» как удаление ВСЕГДА. Но git помечает
исключённые sparse-checkout'ом записи флагом `SKIP_WORKTREE` и считает их **неизменными**:
они остаются в индексе, а на диске их нет.

```
$ git sparse-checkout set keep
$ git ls-files -v -s
S 100644 633ef33d… 0   excluded/f.py     <- S = skip-worktree, на диске отсутствует
H 100644 368cc6ef… 0   keep/f.py
compute_tree = e09b5d3c…      (только keep/f.py)
index_tree   = 56afdf01…      (обе записи)
```

Дерево не совпадает с индексом → `check_precommit` не может вернуть 0 → **третий полный
отказ лесенки**, снова с выходом на `LADDER_SKIP`. Воспроизводится **одинаково на
неисправленном 0.9.0 и на промежуточном прототипе** — то есть дефект предсуществующий, к
симлинкам отношения не имеет.

Уточнение к формулировке ревью: конкретный названный сценарий (подмодуль, исключённый
sparse-checkout'ом) в cone-режиме **не воспроизвёлся** — git оставил gitlink с флагом `H`, и
каталог `vendor/` остался на диске. Но принцип «absent ≠ deleted» верен, и цена его выше
заявленной: страдают ОБЫЧНЫЕ файлы в любом sparse-checkout репозитории, а не подмодули.

## 2. Подход

Четыре дефекта — одна причина: `compute_tree` строит дерево **от рабочего каталога** и
угадывает вид записи по `is_file()`. Всё, что git умеет, а эта модель нет — симлинк,
gitlink, сырые байты, запись без файла на диске — даёт падение либо неверный хэш.

Поэтому чиним не четыре ветки, а **модель**. `compute_tree` начинает строиться от ИНДЕКСА
(полный перечень того, что git считает содержимым дерева) и пере-хэширует с диска только то,
что на диске реально есть. Инвариант формулируется одной фразой:

> `compute_tree(root)` == дерево, которое дал бы `git add -A && git write-tree`.

| источник записи | что берём | почему |
|---|---|---|
| tracked, флаг `S`/`s` (skip-worktree) | mode+oid **из индекса** | git считает запись неизменной; `git add -A` её не трогает. Файла на диске нет — пере-хэшировать нечего, и raciness индекса тут не при чём |
| tracked, есть на диске | пере-хэш с диска (blob / symlink / gitlink) | защита от clean-фильтров и racy-index, ради которой пустой tmp-индекс и заводился |
| tracked, на диске нет, skip-worktree нет | **не добавляем** | настоящее удаление — оно обязано менять дерево |
| tracked, `assume-unchanged` (строчная буква флага) | пере-хэш с диска | `assume-unchanged` прячет правку от git'а; гейт целостности обязан её видеть |
| tracked, stage != 0 (конфликтный merge) | пере-хэш с диска, ОДНА stage-0 запись | так же поступил бы `git add -A`; stage-0 записи в индексе для такого пути нет, и потерять его нельзя |
| untracked, не игнорируется | хэш с диска | «всё изменённое», как и было |

**Приоритет флагов задаётся явно (находка ревью, раунд 3).** `skip-worktree` и
`assume-unchanged` — независимые биты индекса, и `git ls-files -v` кодирует второй
РЕГИСТРОМ буквы первого: запись с обоими битами имеет флаг `s`, а не `S` и не `h`.
Проверено — флаг `s` действительно появляется. Поэтому skip-worktree определяется как
`tag.upper() == "S"`, а регистр читается отдельно и на состав дерева не влияет: всё, что
лежит на диске, пере-хэшируется независимо от `assume-unchanged`. Наивная проверка `tag ==
"S"` вернула бы sparse-файл с `assume-unchanged` в ветку «удалён» и воспроизвела бы
неисполнимую лесенку.

Такая формулировка делает все четыре дефекта структурно невозможными: вид записи больше не
угадывается, а отсутствие на диске больше не значит одно и то же в двух разных ситуациях.
Ветки `elif full.is_file(): … else: continue` в прежнем виде исчезают.

### Р1. Блоб симлинка — по тексту ссылки, в СЫРЫХ байтах

```python
if mode == "120000":
    h = _git_mutate(root, env, "hash-object", "--no-filters", "-w", "--stdin",
                    stdin_bytes=os.readlink(os.fsencode(full)))
else:
    h = _git_mutate(root, env, "hash-object", "--no-filters", "-w", "--", rel)
```

Блоб симлинка в git — ровно текст цели без завершающего перевода строки; `--stdin` не
добавляет ничего. Проверено: `printf '%s' "$(readlink linkdir)" | git hash-object --stdin`
→ `37b86f32…` = то, что git хранит для этой записи.

**Байты, а не текст (находка ревью, high).** `os.readlink(os.fsencode(p))` возвращает
`bytes` — без транскодирования и без суррогатов. `_git_mutate` получает `stdin_bytes` и в
этом режиме запускает subprocess **в двоичном виде** (`text` не задан), а результат
возвращает тем же типом `CompletedProcess`, декодировав только вывод git'а: oid — `ascii`,
диагностику — `utf-8` с `errors="replace"`. Кодировка локали в тракт блоба не попадает
вообще. Проверено на `b"real/\xff\xfename"`: наш блоб `3f606fd5…` = git-ов.

**Канал — `_git_mutate` (ladder_gate.py), не `_trusted_git`.** Обоснование:

- `hash-object -w` пишет в object DB — это мутация, а `_git_mutate` и есть канал мутаций
  (та же санитизация: `_GIT_ENV_ALLOW` + `HOME`/`PATH` + `_GIT_SAFE_ENV` + `_GIT_NEUTRALIZE`).
  Сегодняшний вызов через `_trusted_git` — исторический перекос; переводим **обе** ветки,
  и весь plumbing-блок `compute_tree` (hash-object → update-index → write-tree) становится
  однородным.
- `_trusted_git` — общий стерильный слой, ~50 вызовов по всему деплой-пути и
  подменяемый в `tests/conftest.py:64` лямбдой с фиксированной сигнатурой. Расширять его
  API ради одного вызова — заведомо больший радиус поражения, чем локальный помощник с
  тремя call-site'ами.
- Разница в семантике отказа безвредна: `_trusted_git` вернул бы `None` → `TrustedGitError`,
  `_git_mutate` сам поднимает `TrustedGitError`. Оба конца — один тип.

`_git_mutate` получает keyword-only `stdin_bytes: "bytes | None" = None`. При `None` вызов
байт-в-байт сегодняшний (`text=True`, stdin наследуется), так что два существующих
call-site'а не затронуты.

### Р1b. Подмодули (gitlink, mode 160000) — в дерево, а не мимо

Список gitlink'ов берётся из `git ls-files -s -z` (`<mode> <oid> <stage>\t<path>`), и такие
пути обрабатываются ДО файловой ветки. Семантика — «что бы застейджил `git add -A`»:

| состояние подмодуля | oid в нашем дереве | почему |
|---|---|---|
| инициализирован (`<path>/.git` есть) | `git rev-parse HEAD` **внутри подмодуля** | правда рабочего дерева; сдвинутый HEAD виден и обязан ломать цепочку |
| не инициализирован (пустой каталог) | oid из индекса (`ls-files -s`) | `git add -A` его не трогает — дерево обязано совпасть с индексом |
| флаг `S` (skip-worktree) | oid из индекса | общее правило таблицы §2, не частный случай подмодуля |
| каталога нет вовсе (удалён) | запись **не добавляется** | удаление подмодуля — это изменение дерева, как и удаление файла |
| указатель сдвинут, но не застейджен | HEAD подмодуля (≠ индекс) | `compute_tree` видит сдвиг, но `check_precommit` сверяет маркер с **индексом**: незастейдженный сдвиг в коммит не попадает, поэтому коммит и не блокируется. Блокирует ровно `git add` сдвига без нового прохода |
| HEAD подмодуля не читается (`.git` есть, `rev-parse` упал) | `TrustedGitError` | состояние неизвестно; подставить индекс значило бы объявить совпадение, которого не проверяли. Fail-closed, но теперь **громко** |

Механика проверена: `update-index --add --cacheinfo 160000,<oid>,<path>` принимает коммит,
которого **нет в odb суперпроекта** (`cat-file -e` → False; он лежит в odb подмодуля), и
`write-tree` его переваривает. Собранное дерево репо с подмодулем даёт `21b432a7…` =
`git rev-parse HEAD^{tree}`.

Прочтение HEAD подмодуля идёт тем же санированным каналом (`_git_mutate` с `cwd=<подмодуль>`),
что и в `working_tree_clean` (`codex_review_gate.py:970`) — новых способов звать git нет.

### Р2. Разведение «движок сломан» и «проходы не отмечены»

Три точки:

1. **Текст ошибок `compute_tree`** несёт код возврата и stderr git'а, пропущенные через
   `redact_secrets`: `не посчитать хэш 'link' (git rc=128): fatal: Unable to add (null)…`.
   Так же для `ls-files`, `update-index`, `write-tree`.

2. **`main()`** ловит `TrustedGitError` вокруг `begin`/`mark` и печатает громкий блок
   вместо трейсбека, код возврата **3** (отличен и от 0, и от 2 = «гейт блокирует»):

   ```
   [ladder-gate] ⛔ ДВИЖОК ГЕЙТА СЛОМАН — лесенка НЕИСПОЛНИМА
   <текст ошибки со stderr git>
   Это отказ инфраструктуры, а не непройденный проход: ни begin, ни mark не могут
   отработать, пока причина не устранена. Чинить движок, не обходить гейт.
   ```

   Перехват — **`Exception`, а не только `TrustedGitError`** (см. ниже почему), с печатью
   трейсбека под баннером: трейсбек не проглатывается, а получает шапку, объясняющую, что
   это отказ движка.

3. **`check_precommit`** — ключевое. На пути блокировки (цепочка невалидна) сначала
   пробуется `compute_tree(root)`: если он падает, печатается тот же
   громкий блок «ДВИЖОК СЛОМАН» вместо `_chain_instructions`, exit остаётся **2** (коммит
   по-прежнему блокируется — fail-closed сохранён). Тем же перехватом накрыт и
   `index_tree(root)`, который сегодня умеет уронить хук трейсбеком.

   Смысл: прежде чем сказать «сходи пройди лесенку», убедись, что лесенку физически можно
   пройти. Проба стоит один tree-хэш и только на уже-провальной ветке.

   `LADDER_SKIP` в громком блоке упоминается, но с явной пометкой, что это обход **отказа
   инфраструктуры**, а не забытого прохода, — чтобы аудит-строка не выглядела рутиной.

**Почему ловим `Exception`, а не перечень типов.** Этот баг прожил двое суток именно потому,
что отказ движка выглядел штатно. Перечислять формы отказа — проигрышная игра: три формы
(симлинк-на-директорию, битый симлинк, не-UTF-8 цель) нашлись за один день, а
четвёртая — не-UTF-8 **имя файла** — на macOS даже не воспроизводится (APFS отвергает такие
имена; на ext4 она даст `UnicodeDecodeError` в `ls-files`). Аллоулист форм отказа тут
невозможен, поэтому громким становится **любое** исключение на границе CLI.

Это не «глотание исключений» (CLAUDE.md): исключение не подменяется пустым результатом —
печатается баннер И полный трейсбек, процесс выходит ненулевым кодом, ни одна ветка не
начинает пропускать коммит. Меняется только то, что оператор видит первой строкой.

Заодно декодирование текстового режима `_git_mutate` переводится на
`errors="surrogateescape"`: имена путей от git'а перестают быть точкой отказа, а
суррогаты корректно возвращаются в байты при передаче обратно аргументом subprocess.
**Честно: на APFS это не тестируется** — фикстуру с таким именем создать нельзя
(`OSError: Illegal byte sequence`), поэтому строка идёт как хардненинг под прикрытием
громкого перехвата, а не как проверенный сценарий.

## 4. Инварианты (AGENTS.md / CLAUDE.md)

- Стерильный git-слой: весь доступ к git — через закреплённый бинарь и санированное
  окружение. Соблюдён: `_git_mutate` — тот же слой, новых каналов нет.
- Исключения не глотать: ни один новый `except` не возвращает пустоту; `TrustedGitError`
  перехватывается ровно там, где есть осмысленная реакция (печать диагноза + ненулевой код).
- Fail-closed: ни одна ветка не начинает пропускать коммит. Единственное изменение кодов —
  трейсбек/1 → 3 на `begin`/`mark`; `check_precommit` как блокировал (2), так и блокирует.
- Каждый новый code path — тест, реально входящий в эту ветку (см. §5).

### Как ловится именно баг (тест обязан падать до фикса)

S1 и S2 на текущем коде падают: S1 — `TrustedGitError`, S2 — неравенство для симлинка→файл
(`compute_tree` кладёт блоб содержимого цели при режиме `120000`). S2 покрывает и тот
случай, который «не падает, но врёт», — иначе фикс проверялся бы только по доступности.

S9 падает `UnicodeEncodeError` уже на промежуточной версии фикса — то есть каждый из трёх
дефектов имеет тест, который без своего куска фикса красный.

### Что остаётся принятой ценой

- Не-UTF-8 **имя файла** (не цель симлинка): хардненинг сделан, но на APFS не тестируется;
  прикрыт громким перехватом. Явная непроверенная поверхность.
- Громкий текст детектирует отказ движка **в момент коммита**, а не в момент апгрейда
  плагина. Периодического self-check'а движка нет; вводить его этим патчем не будем.
- Вложенные подмодули (подмодуль внутри подмодуля) не разворачиваются: берётся HEAD
  верхнего уровня, что и есть содержимое gitlink-записи суперпроекта. Это корректно, но
  сдвиг вложенного указателя виден только через изменение HEAD внешнего подмодуля.

## 6. Стоп-политика и итог цикла дизайн-ревью

Ярус `.codex-gate.yaml`: `review.tier: decision` → 3 раунда кодового ревью.
Дизайн-ревью — **один** раунд по правилу скилла, но неразрешённые `critical`/`high` под
бюджет не подпадают: их чинят и перепроверяют. Прошло три раунда, каждый дал подтверждённую
находку выше пола:

| раунд | находка | статус |
|---|---|---|
| 1 | critical: подмодуль = второй полный отказ, а не тихая дыра | воспроизведено, принято, в scope |
| 1 | high: `text=True` роняет не-UTF-8 цель симлинка | воспроизведено, принято, байтовый тракт |
| 2 | high: absent ≠ deleted (SKIP_WORKTREE) | воспроизведено и оказалось ШИРЕ заявленного (обычные файлы, не подмодули) → подход перестроен на индекс |
| 3 | high: комбинированный флаг `s` | подтверждено; реализация уже соответствовала (`tag.upper()`), закрыт пробел в таблице и в тестах |

**Цикл закрыт на раунде 3.** Находка раунда 3 не потребовала изменения подхода — только
явной формулировки приоритета флагов и двух тестов. Признак сходимости по стоп-политике:
последний раунд не нашёл дефекта в самом подходе. Дальнейшая проверка — код-ревью на
реализации, где находки воспроизводимы, а не гипотетичны.

Собственная находка стенда, которую ревью не называло: при переходе на индекс пути со
stage != 0 выпадали из дерева ЦЕЛИКОМ (их нет ни среди stage-0 записей, ни среди untracked).
Поймано сценарием S21 до применения патча к исходнику.

## 7. Что дизайн НЕ предусмотрел (дописано по итогам реализации)

Дизайн-ревью закрылось на «модели от индекса» как на достаточной. Реализация и последующие
проходы показали, что главного вопроса дизайн не задал вовсе, и записывать это надо честно.

**Вопрос, которого не было: откуда берётся запись, если не с диска.** Переход на индекс как
базу молча ввёл второй источник правды, а индекс наполняет ПРОВЕРЯЕМАЯ сторона. Из этого
вышли четыре формы одного канала подмены, найденные уже по коду:

| нашёл | форма | итог |
|---|---|---|
| код-ревью, р.1 | `skip-worktree` при файле НА диске | застейдженное злое хэшируется вместо доброго с диска |
| код-ревью, р.2 | `skip-worktree` при отсутствующем файле | то же, но ревьюер не видит вообще ничего |
| код-ревью, р.3 | деинициализированный подмодуль | злой указатель, содержимого на диске нет |
| стенд (не назывался ревью) | `skip-worktree` на файле, которого нет в HEAD | сравнивать не с чем |
| security-ревью | **подмена самого базиса**: `git symbolic-ref HEAD` на чужую ветку | лесенка проходится целиком, ledger полон, деплой-гейт доволен, бэкдор в коммите |

Первые три чинились по одной — это и была ошибка. Правило верного уровня общности одно:
**запись, взятая из индекса, а не пере-хэшированная с диска, невидима ревьюеру и проходит,
только если не менялась с последнего коммита** — и оно закрыло заодно четвёртую форму,
которую никто не называл. Живёт одной функцией `_from_index_unseen` с единым предикатом
`_is_unseen` именно поэтому: разъехавшиеся копии условия и дали три раунда подряд.

Пятая форма — отдельного рода: базис сравнения тоже принадлежит проверяемой стороне. `HEAD`
переставляется `git symbolic-ref` без единой правки индекса и дерева, то есть не трогая
ровно то, что лесенка хэширует. Лечится тем, что исключение перепроверяется на pre-commit
против HEAD, на который коммит РЕАЛЬНО ложится. Сверять там `compute_tree == index_tree`
целиком нельзя: незастейдженная правка в дереве законна и коммита не касается.

**Урок для следующего дизайна такого рода:** вводя второй источник правды в chokepoint
целостности, спрашивать не «покрыты ли формы записей», а «кто контролирует этот источник и
что он может им сказать». Перечисление форм — работа для кода-ревью, где формы
воспроизводимы; на дизайне размножаются гипотезы, а не факты.
