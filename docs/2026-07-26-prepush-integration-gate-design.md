# Pre-push интеграционный гейт (тикет A)

Дата: 2026-07-26 (ред. 5 + микро-правка). **Статус: цикл ревью закрыт на хард-капе
(5 раундов), спека одобрена к реализации с документированными остатками §9.**

История редакций — не формальность, а суть тикета: каждая правка вызвана найденным дефектом.

- **ред. 1** — не прошла: переиспользовала `empirical.test_command` (написанную для запуска в
  корне репо) во временном worktree → **ложные зелёные**; §2 проверял посылки о существующем
  коде и не проверял следствие.
- **ред. 2** — не прошла: ввела отдельную «герметичную» команду, но негерметичность —
  **дефолт** Python/Node-проектов, а не злой умысел, поэтому главный сценарий по-прежнему мог
  молча пройти. Заодно создала путь, где `warn` при неудачном fetch давал полный тихий пропуск.
- **ред. 3** — не прошла: **обещание сужено до проверяемого** (решение человека) — это приняли,

- **ред. 4** — не прошла: референс И4 переведён на `<remote sha>` (это приняли), но `unreadable`
  был слит с `absent` в «проход» — fail-open при непрочитанном предыдущем tip'е; плюс пропуск
  строки базовой ветки уносил с собой И4.
- **ред. 5** (эта) — `unreadable` отделён от `absent` и блокирует; пропуск стал по-проверочным,
  а не по-строчным; добавлен детектор пересоздания ветки. Ревью нашло одну находку выше пола —
  безусловное «нули → введение» в E4а/C9a обходило свежий детектор E4г (нормативный текст отстал
  от прозы, тот же класс, что и трижды за этот цикл) — исправлено микро-правкой вместе с
  определением тождества базовой ветки по паре `(remote, branch)`. Дальше — реализация без
  нового адверсариального раунда.

## 1. Проблема и обещание

### 1.1 Что чинится

Разработка идёт от базы, устаревшей к началу работы:

1. **Конфликты обнаруживаются на GitHub**, а не локально, где дешевле. ← **это гейт решает**
2. **Тесты зелены на ветке и на main по отдельности, но красны на слиянии** (семантический
   конфликт). ← **это гейт НЕ гарантирует**, см. §1.2

Проверено 2026-07-26: в плагине нет ни одного обращения к `fetch`/`upstream`/отставанию.

### 1.2 Почему «тесты на слиянии» локально не гарантируются

Проба — отдельный worktree со смерженным деревом. Но исполняемый код определяется не деревом:

- `pip install -e .`, venv в `PATH`, `NODE_PATH`, монорепо: pytest соберёт тесты из пробы,
  а `import project` разрешится через `.pth`/egg-link в **настоящее** дерево. Дерево верное,
  исполняется код неслитый → **зелёный, не выполнив слияния**;
- обратное: gitignored (`.venv/`, `node_modules/`, артефакты) в пробе отсутствует → красный
  по причинам, не связанным со слиянием.

Это **дефолтная** раскладка Python/Node-проектов. Проверить герметичность в общем виде гейт не
может (для этого нужна изоляция уровня контейнера, которую способен обеспечить только сам
проект). Ред. 2 пыталась закрыть это утверждением проекта «моя команда герметична» — не
работает: `merge_test_command: /bin/true` формально «задана», сценарий выглядит покрытым.

**Отсюда обещание гейта, сформулированное точно:**

> Гейт доказывает: **слияние с базой не конфликтует**.
> Гейт НЕ доказывает: что слитый код работает.
> Красный результат тестов — всегда повод остановиться. **Зелёный не означает ничего** и
> сопровождается пометкой ВСЕГДА, а не только когда команда не задана.

## 2. Область: чего гейт не делает

Проверено по коду; посылки верны, но вывод ред. 1 был неверен:

- `check_range` действительно освобождает merge-коммиты;
- деплой-гейт действительно commit-bound (кэш `(head_sha, diff_sha256, reviewers)`).

**Но устаревшее ревью этим не лечится:** гейт намеренно **не вливает** main в ветку, поэтому
после зелёного пуша HEAD остаётся неслитым и кэш вердикта для него по-прежнему попадает.
Устаревшая база лечится только когда HEAD реально сдвинется. Локально это не задача гейта;
серверная сторона — inframon.

Отдельно: **ребейз на main — не merge-коммит**, освобождение merge-коммитов к нему не
относится (существующий остаток «ребейз стирает ledger»).

## 3. Эмпирика (измерено 2026-07-26, git 2.50.1)

`git merge-tree --write-tree <base> <sha>`:

| Случай | Код | stdout |
|---|---|---|
| чистое слияние | `0` | одна строка — OID дерева |
| конфликт | `1` | OID, строки стадий `1/2/3` с путями, пустая строка, `CONFLICT (content): …` |
| **прочее** (битый OID, partial clone, порча) | **≠0,1** | не специфицировано → трактуем как «неизвестно» |

Материализация — измерена:

```bash
TREE=$(git merge-tree --write-tree "$BASE" "$SHA")
C=$(git commit-tree "$TREE" -p "$BASE" -p "$SHA" -m "integration probe")
git worktree add -q --detach "$W" "$C"          # одним шагом
```

Замер показал: содержимое пробы действительно смерженное; незакоммиченный файл настоящего дерева
не тронут; `worktree remove --force` + `prune` возвращают список worktree к исходному.

**`core.hooksPath` в пробе НЕ изолирован** — наследуется из общего конфига репозитория
(проверено). Нейтрализация измерена: `GIT_CONFIG_COUNT=1 GIT_CONFIG_KEY_0=core.hooksPath
GIT_CONFIG_VALUE_0=<несуществующий>` глушит хук и наследуется вложенными процессами
(проверено через `sh -c 'git commit …'`).

Не измерено, объявлено остатком (§9): submodules, LFS, sparse-checkout.

## 4. Инварианты

- **И1.** Гейт не изменяет рабочее дерево пользователя и не разрешает конфликты автоматически.
  `fetch` двигает remote-tracking ref'ы — названное исключение.
- **И2.** Проверка конфликтов выполняется на **пушимом** SHA каждой строки stdin, не на `HEAD`.
- **И3.** **Любой** неизвестный исход git — код `merge-tree` вне `{0,1}`, неудача `worktree add`,
  сбой `fetch` — трактуется как «неизвестно», НЕ как «чисто». В частности: если tip базы не
  обновлён, гейт **не имеет права** заключить «интегрировать нечего».
- **И4.** Ослабление `integration.*` в самом пушимом коммите не одобряет само себя.
- **И5.** Зелёный результат тестов не порождает утверждения о работоспособности слияния;
  пометка о этом печатается всегда, когда тесты запускались.
- **И6.** Проба не порождает побочных эффектов в общей бухгалтерии: git-хуки отключены и при
  материализации, и при прогоне.
- **И7.** Временный worktree удаляется best-effort + `prune` на старте (SIGKILL не выполняет
  `finally` — это остаток, а не обещание).
- **И8.** Гейт молчит в проектах без `.codex-gate.yaml` (выход 0).
- **И9.** Обход существует, требует причину и аудируется.

## 5. Конструкция

Точка — шим `.githooks/pre-push`: уровень git ловит пуш даже мимо агента.

**Вход.** По строке `<local ref> <local sha> <remote ref> <remote sha>`; используется
`<local sha>` (И2). Пропуск — **по проверкам, а не по строке целиком**:

| Строка | И4 (анти-самоослабление) | Предсказание слияния и тесты |
|---|---|---|
| удаление (`local sha` нули) | пропуск (читать нечего) | пропуск |
| тег (`refs/tags/`) | пропуск (в main через тег не попадают) | пропуск |
| **пуш самой базовой ветки** | **ВЫПОЛНЯЕТСЯ** | пропуск (сливать с собой нечего) |
| обычная ветка | выполняется | выполняется |

Базовая ветка — отдельная строка не случайно: ред. 4 пропускала её целиком, и прямой коммит в
main, ослабляющий `integration.*`, уходил вообще без проверки И4 (найдено ревью ред. 4).
Предсказание слияния для main действительно неприменимо, анти-самоослабление — вполне.

**Конфиг.** `integration.*` читается из пушимого коммита. Отсутствие секции доказывается
`git ls-tree`, а не сбоем `git show` (сбой ≠ «нет файла» — тот же приём, что
`_config_section_at_ref`); нечитаемо/битый YAML = «неизвестно» → блок.

**Анти-самоослабление (И4).** Референс — **`<remote sha>` пушимого ref'а** (предыдущий принятый
tip этой же ветки), НЕ `base_ref`. Нули означают «ветки на remote не было» — и трактуются как
`absent` только если локального tracking-ref'а тоже нет (иначе это пересоздание, см. ниже).

Почему не база: у `_empirical_gate` baseline — последнее **задеплоенное** состояние, и оно
двигается вперёд после каждого деплоя. `origin/main` не двигается до мержа, поэтому пока в main
нет секции, КАЖДЫЙ пуш ветки выглядел бы «введением», и правило не сработало бы ровно на том
коммите, который прописывает себе ослабление (найдено ревью ред. 3).
`<remote sha>` двигается с каждым пушем ветки — это и есть верный аналог.

**Пересоздание ветки.** Удаление ветки на remote и повторный пуш дают нули, то есть сбрасывают
референс тише, чем аудируемый обход. Дешёвый детектор: нули в `<remote sha>` ПРИ существующем
локальном `refs/remotes/<remote>/<branch>` — признак пересоздания, а не новой ветки → блок с
предложением `INTEGRATION_CONFIG_CHANGE`. Ложное срабатывание возможно, если ветку удалил кто-то
другой и локальный tracking-ref устарел (лечится `git fetch --prune`); гейт fail-safe, поэтому
блок с внятной причиной допустим. Остаток §9.

**Измерено на реальном пуше 2026-07-26** (хук печатал stdin):

| Ситуация | `remote_sha` |
|---|---|
| первый пуш новой ветки | `0000000…` → `absent` (совпадает с трактовкой выше) |
| обычный второй пуш | предыдущий tip ветки |
| **force-push с перезаписью истории (`--amend` + `--force`)** | **предыдущий tip, НЕ нули** |

Третья строка — ключевая для соундности: перезапись истории не сбрасывает референс в «absent»,
поэтому ослабление, протащенное через force-push, всё равно сравнивается с принятым ранее
состоянием. (Ослабление в ветке, впервые пушимой в ДРУГОЙ remote, получит нули и пройдёт — но
это ветка, которая ещё никуда не влита; в main она попадёт только через свой обычный маршрут.)

| `<remote sha>` | Состояние секции в нём | В пушимом коммите | Решение |
|---|---|---|---|
| нули, локального tracking-ref'а НЕТ (новая ветка) | — | любое | **проход** — ВКЛЮЧЕНИЕ гейта |
| нули, локальный tracking-ref ЕСТЬ (пересоздание) | — | любое | **БЛОК** без подтверждения (E4г) |
| непустой | `absent` (ДОКАЗАНО: `ls-tree` прочитан, пути нет) | любое | проход — включение |
| непустой | **`unreadable`** (сбой `ls-tree`/объекта нет локально) | любое | **БЛОК** — см. ниже |
| непустой | `enabled` | совпадает | проход |
| непустой | `enabled` | отличается | **блок** без `INTEGRATION_CONFIG_CHANGE=1` с причиной |
| любой | любое | `unreadable` | блок (состояние гейта не подтвердить) |

**`unreadable` ≠ `absent` — это отдельная строка, и она блокирует.** Ошибка ред. 4: они были
слиты в одну «проход». Путь к ней обыденный: коллега запушил tip, который мы никогда не фетчили,
затем force-push → `ls-tree <remote_sha>` локально падает → «введение» → ослабление проходит.
Существующий `_config_section_at_ref` эту разницу соблюдает намеренно (сбой `ls-tree` —
не доказательство отсутствия), и здесь должно быть так же (И3). Лечится `git fetch` нужного
tip'а либо аудируемым `INTEGRATION_CONFIG_CHANGE`.

Первый пуш ветки проходит свободно (bootstrap-дедлок первой версии правила исправлен), а
последующий пуш, ослабляющий уже выставленную политику, — нет. Силу двух произвольных политик
сравнить нельзя (`merge_test_command: pytest` → `true` эффективно снимает проверку), поэтому
блокируется ЛЮБАЯ смена.

Проверка выполняется **до** шага fetch: она сетевого доступа не требует, и её нельзя терять
на политике `on_fetch_failure`.

Мотив: без этого коммит, прописавший себе `on_fetch_failure: warn` и
`merge_test_command: "true"`, сам себя одобряет — а для `integration.*` pre-push единственная
линия защиты, в отличие от `code_paths`, где второй линией стоит Codex-ревью деплой-диффа.

`INTEGRATION_CONFIG_CHANGE` агент может выставить сам — это **тот же класс аудируемого обхода**,
что `EMPIRICAL_SKIP`/`LADDER_SKIP`, и та же граница: механизм делает изменение видимым, а не
невозможным. Иных гарантий локально не бывает (см. закрытый тикет B1).

**Алгоритм на строку:**

0. Анти-самоослабление (И4, выше): сравнить секцию в `<remote sha>` и `<local sha>`. Блок при
   ослаблении без подтверждения. Сети не требует, поэтому идёт первым.
1. База: `integration.base_ref`, по умолчанию `origin/main` (ключ обязателен для форков: пуш в
   `origin`, база в `upstream`).
2. `git fetch` базы с таймаутом.
   - успех → шаг 3;
   - сбой и `on_fetch_failure: block` (по умолчанию) → **блок** с причиной;
   - сбой и `on_fetch_failure: skip-audited` → **выход с громкой пометкой «база неизвестна,
     слияние НЕ проверялось»** + запись в аудит при КАЖДОМ срабатывании. Шаги 3-5 НЕ
     выполняются: считать `rev-list` против неосвежённой базы и получить 0 значило бы объявить
     «интегрировать нечего», не зная состояния базы (И3) — ред. 2 именно так и делала.

     Значение названо `skip-audited`, а не `warn`, сознательно: это **не «предупредить и
     продолжить проверку», а полный пропуск единственного обещания гейта** — то есть
     конфигурируемый аудируемый обход того же класса, что `INTEGRATION_SKIP`. Правило проекта
     «настроенный источник отказал → блок, без деградации» этим НЕ отменяется: деградация
     возможна только по явному решению оператора, записанному в конфиг и в аудит. Остаток §9.
3. `git rev-list --count <sha>..<base>` == 0 → интегрировать нечего, пропуск.
4. `merge-tree --write-tree <base> <sha>`: `rc=1` → **блок** со списком конфликтующих путей;
   `rc=0` → шаг 5; **иначе → блок** (И3).
5. Тесты (необязательны, ничего не гарантируют):
   - `integration.merge_test_command` не задана → пропуск + пометка «конфликтов нет; тесты на
     слиянии не запускались»;
   - задана → материализовать пробу в уникальный путь (`pid` + короткий SHA), выполнить
     с `cwd=$W`, argv без shell, таймаут `integration.test_timeout`, git-хуки отключены (§3).
     Ненулевой код/таймаут → **блок** с выводом. Успех → пропуск + пометка «тесты на пробе
     зелёные, но это НЕ доказывает работоспособность слияния: команда могла исполнить код из
     настоящего дерева (editable install/venv)» — печатается ВСЕГДА (И5).

     **Отдельный обход для тестов: `INTEGRATION_TESTS_SKIP=1` с причиной.** Красные тесты могут
     быть вызваны негерметичным окружением пробы, а не слиянием (§1.2). Если единственным
     обходом был бы `INTEGRATION_SKIP`, оператор под давлением ложных красных отключал бы **весь
     гейт вместе с проверкой конфликтов** — то есть необязательный сигнал стоил бы единственного
     обещания. Разделение обходов убирает это давление (найдено ревью ред. 3).
6. Контроль побочного эффекта (И1): `git status --porcelain` настоящего дерева до и после
   прогона; расхождение → блок «команда изменила рабочее дерево». Сравниваются только
   отслеживаемые пути; записи в gitignored пути (кэши) не детектируются, параллельная правка
   оператором даёт ложный блок — оба остатка названы в §9.
7. `finally`: удалить worktree; `worktree prune` перед созданием нового.

## 6. Бизнес-сценарии и приёмочные критерии

**С1 — база не двигалась.** Пуш проходит; проверка дешёвая.

**С2 — база ушла, слияние чистое.** Пуш проходит; в аудите база и её SHA.

**С3 — конфликт.** Блок со списком файлов; рабочее дерево, включая незакоммиченное, не
изменено. **Главный приёмочный критерий: это единственное, что гейт обещает.**

**С4 — тесты на пробе красные.** Блок с выводом. (Причина может быть и семантическим
конфликтом, и негерметичным окружением — гейт их не различает и не утверждает, что различает.)

**С5 — тесты на пробе зелёные.** Пуш проходит **с пометкой, что это ничего не доказывает**.
Приёмка: пометка присутствует ВСЕГДА, а не только при отсутствии команды. **Критерий на И5.**

**С6 — `merge_test_command` — no-op (`/bin/true`).** Поведение то же, что С5: пометка печатается,
покрытым сценарий не выглядит. В ред. 2 это был худший случай (тише отсутствия команды).

**С7 — `fetch` не удался, политика `block`.** Блок с причиной.

**С8 — `fetch` не удался, политика `skip-audited`.** Проход с пометкой «слияние НЕ проверялось»;
merge-tree и тесты НЕ выполняются. Приёмка: в выводе нет утверждения «интегрировать нечего».
**Критерий на И3** (в ред. 2 здесь был тихий пропуск).

**С9 — пушимый коммит меняет УЖЕ ВКЛЮЧЁННУЮ `integration.*`.** Блок без аудируемого
подтверждения. **Критерий на И4.**

**С9а — ПЕРВЫЙ пуш НОВОЙ ветки вводит `integration.*`.** Проход: включение гейта — не
ослабление (`<remote sha>` = нули И локального tracking-ref'а нет). Приёмка: bootstrap не
блокируется.

**С9в — ветка ПЕРЕСОЗДАНА** (удалена на remote и запушена снова) с ослабленной секцией:
`<remote sha>` = нули, но локальный tracking-ref существует → блок без аудируемого
подтверждения. Приёмка: тихий сброс референса И4 невозможен.

**С9б — ветка вводит политику, а СЛЕДУЮЩИМ пушем её ослабляет** (`block` → `skip-audited`,
`merge_test_command: pytest` → `true`), причём в `origin/main` секции нет вовсе. Блок без
подтверждения. **Критерий на выбор референса:** при сравнении с базой этот случай проходил бы
свободно — ровно та атака, ради которой И4 существует (найдено ревью ред. 3).

**С10 — секция отсутствует в пушимом коммите.** Отсутствие доказано `ls-tree`; поведение —
дефолты. Сбой `git show` при существующем файле → «неизвестно» → блок.

**С11 — пуш ref'а, отличного от текущей ветки.** Проверяется пушимый `local sha`, не `HEAD`.

**С12 — пуш нескольких ref'ов, часть пропускается** (тег + ветка; базовая ветка + фича).
Каждая строка обрабатывается независимо; блок любой блокирует команду.

**С13 — `merge-tree` вернул код вне `{0,1}`.** Блок (И3).

**С14 — вложенный `git commit` внутри тест-команды.** Наши pre/post-commit не запускаются,
ledger для дерева-пробы не появляется (И6, механика измерена в §3).

**С15 — команда изменила настоящее дерево.** Блок «негерметична» (И1).

**С16 — репозиторий в середине ребейза / остался worktree от убитого хука.** `prune` на старте;
неудача `worktree add` → блок (И3).

**С17 — SIGKILL посреди прогона.** Worktree остаётся мусором, подчищается следующим запуском.

**С18 — проект не онбординат.** Выход 0 (И8). Отдельно: пушимый коммит без `.codex-gate.yaml`
при онбордженном рабочем дереве — трактуется по пушимому коммиту (нет конфига → дефолты).

**С19 — обход всего гейта.** `INTEGRATION_SKIP=1` с ОБЯЗАТЕЛЬНОЙ причиной; причина в аудите.

**С19а — обход только тестов.** `INTEGRATION_TESTS_SKIP=1` с причиной: проверка конфликтов
ВЫПОЛНЯЕТСЯ, тесты пропускаются. Приёмка: ложные красные тесты не заставляют жертвовать
единственным обещанием гейта.

**С20 — submodules / LFS / sparse-checkout.** Проба может быть неполной; пометка в выводе.

### Денежных краевых случаев нет

Гейт только запрещает пуш. Риск ложного зелёного по тестам присутствует, но **не является
ложным зелёным гейта**: гейт про тесты ничего не обещает (И5), и это отражено в С5/С6.

## 7. EARS

- **E1.** THE система SHALL обрабатывать каждую строку stdin и использовать её `<local sha>`.
- **E2.** IF строка описывает удаление или тег, THEN SHALL пропустить её целиком.
- **E2а.** IF пушимая пара `(remote, branch)` совпадает с разобранным `integration.base_ref`,
  THEN SHALL пропустить предсказание слияния и тесты, но SHALL выполнить проверку И4.
  Сравнение SHALL идти по паре, а НЕ по одному имени ветки: у форка (`origin/main` пушится,
  база — `upstream/main`) совпадение только по имени пропустило бы предсказание слияния —
  fail-open единственного обещания.
- **E3.** THE система SHALL читать `integration.*` из пушимого коммита; отсутствие секции SHALL
  доказываться `ls-tree`, а нечитаемость SHALL трактоваться как «неизвестно» → блок.
- **E4.** IF секция `integration.*` в `<remote sha>` пушимого ref'а `enabled` И в пушимом
  коммите отличается, THEN SHALL заблокировать пуш без аудируемого подтверждения с причиной.
- **E4а.** WHERE `<remote sha>` — нули **И локального `refs/remotes/<remote>/<branch>` нет**,
  ЛИБО секция в непустом `<remote sha>` ДОКАЗАННО отсутствует (`ls-tree` прочитан, пути нет),
  THE система SHALL считать её появление включением гейта и SHALL NOT блокировать пуш по этой
  причине. (Безусловная формулировка «нули → введение» обходила бы E4г — найдено ревью ред. 5.)
- **E4в.** IF `<remote sha>` непустой И секцию в нём прочитать не удалось, THEN THE система SHALL
  заблокировать пуш (сбой чтения — не доказательство отсутствия, И3).
- **E4г.** IF `<remote sha>` — нули, но локальный `refs/remotes/<remote>/<branch>` существует,
  THEN THE система SHALL трактовать это как пересоздание ветки и заблокировать пуш без
  аудируемого подтверждения.
- **E4б.** THE система SHALL сравнивать секцию с `<remote sha>` пушимого ref'а, а НЕ с
  `integration.base_ref`.
- **E5.** IF обновить tip базы не удалось, THEN SHALL применить `on_fetch_failure`, записать
  политику и причину в аудит при каждом срабатывании, и SHALL NOT выполнять сравнение
  отставания, предсказание слияния и тесты.
- **E5а.** THE система SHALL выполнять проверку И4 ДО шага fetch и SHALL NOT пропускать её
  ни при какой политике `on_fetch_failure`.
- **E6.** IF `<local sha>` не отстаёт от **обновлённой** базы, THEN SHALL пропустить строку.
- **E7.** IF предсказание слияния сообщает конфликт, THEN SHALL заблокировать пуш, перечислить
  конфликтующие пути и SHALL NOT изменять рабочее дерево.
- **E8.** IF код `merge-tree` вне `{0,1}` ИЛИ `worktree add` не удался, THEN SHALL заблокировать
  пуш с диагностикой.
- **E9.** THE система SHALL NOT использовать `empirical.test_command` для прогона на слиянии.
- **E10.** WHERE `merge_test_command` задана, THE система SHALL выполнить её в пробе с
  отключёнными git-хуками и SHALL заблокировать пуш при ненулевом коде или таймауте.
- **E11.** WHEN тесты выполнялись и завершились успешно, THE система SHALL напечатать, что
  результат НЕ доказывает работоспособность слияния.
- **E12.** WHERE `merge_test_command` не задана, THE система SHALL напечатать, что тесты на
  слиянии не запускались.
- **E13.** IF команда изменила отслеживаемые файлы рабочего дерева, THEN SHALL заблокировать
  пуш и сообщить о негерметичности.
- **E14.** THE система SHALL отключать git-хуки и при материализации пробы, и при прогоне.
- **E15.** WHEN проверка завершается любым исходом, THE система SHALL best-effort удалить
  worktree и SHALL выполнять `prune` перед созданием нового.
- **E16.** IF задан обход всего гейта, THEN SHALL требовать причину, пропустить пуш и записать
  причину.
- **E16а.** IF задан обход только тестов, THEN SHALL выполнить проверку конфликтов, пропустить
  тесты, требовать причину и записать её.
- **E17.** WHERE проект не онбординат, THE система SHALL завершиться с кодом 0.

## 8. Отвергнутые подходы

- **Автоматический pull/rebase перед пушем.** Мутация рабочего дерева за спиной человека.
- **Прогон тестов на ветке вместо слияния.** Не даёт вообще ничего нового.
- **Переиспользовать `empirical.test_command`** (ред. 1). §1.2.
- **Считать «герметичность» утверждением проекта и обещать тесты на слиянии** (ред. 2).
  Негерметичность — дефолт, а no-op команда выглядит покрытием. Обещание сужено вместо
  подпирания утверждениями.
- **Требовать контейнер для запуска тестов.** Технически закрывает §1.2, но исключает
  большинство проектов; отвергнуто по применимости, не по корректности. Может вернуться как
  необязательный строгий режим.
- **Автоматически инвалидировать approve при отставании.** Вне области (§2): ре-ревью
  происходит, когда HEAD реально сдвинется.
- **Проверка на SessionStart вместо pre-push.** База уезжает за сессию.

## 9. Документированные остатки

1. **Тесты на пробе ничего не гарантируют** (§1.2). Это не остаток гейта, а его явно
   заявленная граница (И5): гарантия — только отсутствие конфликтов.
2. **Контроль побочного эффекта видит только отслеживаемые пути**: запись в gitignored кэши
   не детектируется; параллельная правка оператором во время прогона даёт ложный блок.
3. **SIGKILL оставляет worktree**; подчищается следующим запуском.
3б. **Детектор пересоздания ветки даёт ложный блок**, если ветку удалил кто-то другой и
   локальный tracking-ref устарел; лечится `git fetch --prune`.
3а. **`on_fetch_failure: skip-audited` — конфигурируемый fail-open единственного обещания.**
   Хронический сбой fetch (VPN, SSO, окружение без сети) превращает гейт в громкий no-op.
   Дефолт `block` выбран именно поэтому; значение названо `skip-audited`, чтобы никто не читал
   его как «предупредили и всё равно проверили».
4. **submodules / LFS / sparse-checkout** в пробе могут быть неполными.
5. **Слияние проверяется с tip базы на момент пуша**; уедет база до мержа на GitHub —
   результат снова не проверен. Локально не лечится (inframon).
6. **Ребейз** не создаёт merge-коммит и стирает ledger — существующий остаток.
7. **Дочерний процесс может сбросить `GIT_CONFIG_COUNT`** и вернуть себе хуки; нейтрализация
   (И6) — defense-in-depth, не доказательство.

## 10. Открытые вопросы

- Дефолт базы: `origin/main` жёстко или вывод из `origin/HEAD`.
- Кэш «пара (base tip, local sha) уже проверена», чтобы повторный пуш не гонял тесты снова.
