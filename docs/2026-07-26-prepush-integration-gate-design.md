# Pre-push интеграционный гейт (тикет A)

Дата: 2026-07-26. Статус: спека, ревью не пройдено.

## 1. Проблема

Разработка идёт от базы, которая устарела в момент начала работы: перед первой правкой никто
не подтягивает `origin/main`. Следствия, по возрастанию неприятности:

1. **Конфликты обнаруживаются на GitHub**, а не локально, где их дешевле разрешать.
2. **Тесты зелены на ветке и на main по отдельности, но красны на их слиянии.** Семантический
   конфликт (в main поменяли сигнатуру/контракт/инвариант, которым мы пользуемся) мержится
   чисто и ломается только в объединении.
3. **Ревью смотрело не туда.** Codex-ревью диффа считается от устаревшего merge-base, поэтому
   несовместимость с актуальным main физически не попадает в поле зрения ревьюера.

Проверено 2026-07-26: в плагине нет ни одного обращения к `fetch`/`upstream`/отставанию —
класс не покрыт вообще.

## 2. Область: чего гейт НЕ делает

Проверено по коду перед проектированием, чтобы не строить лишнее:

- `check_range` уже **освобождает merge-коммиты** от лесенки (п.1 её docstring): итог диапазона
  независимо ревьюит деплой-гейт.
- Деплой-гейт **commit-bound**: после вливания main меняется HEAD, кэш вердикта старого SHA
  не применяется, ревью пересчитывается.

Поэтому гейт **не** изобретает инвалидацию approve и не переоткрывает лесенку. Его задача
узкая: не дать уйти в GitHub тому, что конфликтует или краснеет после слияния.

## 3. Эмпирика (замер 2026-07-26, git 2.50.1)

`git merge-tree --write-tree <base> <head>` — предсказание слияния **без касания рабочего
дерева**:

| Случай | Код возврата | stdout |
|---|---|---|
| чистое слияние | `0` | одна строка — OID результирующего дерева |
| конфликт | `1` | OID дерева, затем строки стадий `1/2/3` с путями, пустая строка, затем `CONFLICT (content): ...` |

Материализация результата для прогона тестов (проверено, грязное рабочее дерево не пострадало):

```bash
TREE=$(git merge-tree --write-tree "$BASE" HEAD)      # rc=0
C=$(git commit-tree "$TREE" -p "$BASE" -p HEAD -m "integration probe")
git worktree add -q --detach "$W" && git -C "$W" checkout -q --detach "$C"
# тесты гоняются в $W; исходное дерево, включая незакоммиченные файлы, не тронуто
```

## 4. Инварианты

- **И1.** Гейт **никогда** не изменяет рабочее дерево пользователя и не разрешает конфликты
  автоматически: слияние и резолв — решение человека.
- **И2.** Тесты гоняются на **смерженном** дереве, а не на ветке: зелёная ветка ничего не
  доказывает про результат слияния.
- **И3.** Неизвестное состояние базы (fetch не удался) ≠ «база не изменилась». Молчаливого
  фолбэка к «всё хорошо» нет.
- **И4.** Временный worktree удаляется при любом исходе, включая падение и таймаут.
- **И5.** Обход существует и аудируется (симметрично `LADDER_SKIP`/`EMPIRICAL_SKIP`).

## 5. Конструкция

Точка — шим `.githooks/pre-push` (тот же механизм резолва версии плагина, что у существующих
хуков). Уровень git выбран сознательно: он ловит пуш даже мимо агента и работает на любом
хосте-агенте, включая Codex (тикет C).

Алгоритм на каждый пушимый ref (stdin pre-push: `<local ref> <local sha> <remote ref> <remote sha>`):

1. Удаление ветки (`local sha` из нулей) → пропуск.
2. База: `integration.base_ref` из `.codex-gate.yaml`, по умолчанию `origin/main`. Пуш самой
   базовой ветки → проверка отставания неприменима (git сам отвергнет non-fast-forward).
3. `git fetch` базы с таймаутом. Сбой/таймаут → **блок** с причиной: сеть до remote заведомо
   нужна для самого пуша, поэтому неудачный fetch здесь аномалия, а не норма.
4. `git rev-list --count HEAD..<base>` == 0 → интегрировать нечего, пропуск.
5. Иначе `merge-tree --write-tree`:
   - rc=1 → **блок**, печать конфликтующих путей и инструкции разрешить локально;
   - rc=0 → материализация во временный worktree и прогон `empirical.test_command`;
     ненулевой код/таймаут → **блок** с выводом; успех → пропуск.
6. Worktree удаляется в `finally`.

Если `empirical.test_command` не задан, шаг 5б пропускается с громкой пометкой: гейт проверил
только конфликты — иначе оператор решит, что тесты на слиянии зелёные.

## 6. Бизнес-сценарии и приёмочные критерии (BSAC)

**С1 — база не двигалась.** Пуш проходит, лишней работы нет (проверка дешёвая: `rev-list --count`).

**С2 — база ушла вперёд, слияние чистое, тесты зелёные.** Пуш проходит; в аудит пишется, что
проверка проводилась и на каком SHA базы.

**С3 — конфликт.** Пуш блокирован, названы конфликтующие файлы; рабочее дерево не изменено
(в т.ч. незакоммиченные файлы на месте). **Главный приёмочный критерий на И1.**

**С4 — семантический конфликт.** Слияние чистое, но тесты на смерженном дереве красные. Пуш
блокирован, показан вывод тестов. **Главный приёмочный критерий на И2** — ради него всё и делается.

**С5 — fetch недоступен.** Блок с причиной, не «похоже, всё в порядке».

**С6 — тест-команда не задана.** Пуш проходит после проверки конфликтов, но с явной пометкой,
что тесты на слиянии не проверялись.

**С7 — грязное рабочее дерево.** Гейт отрабатывает, ничего не трогает, незакоммиченные правки
на месте.

**С8 — падение/таймаут в середине.** Временный worktree не остаётся мусором; повторный запуск
не спотыкается об остатки прошлого.

**С9 — обход.** `INTEGRATION_SKIP=1` с причиной: пуш проходит, факт и причина в аудите.

**С10 — пуш нескольких веток разом.** Каждая проверяется отдельно; блок хотя бы одной блокирует
команду (git-семантика pre-push).

### Денежных краевых случаев нет

Гейт только запрещает пуш и не трогает внешние системы, состояние и деньги. Риск — ложный блок
(fail-safe), поэтому обход обязателен и аудируем.

## 7. EARS

- **E1.** WHEN выполняется `git push` ветки, THE система SHALL определить актуальный tip базы
  перед решением.
- **E2.** IF получить tip базы не удалось, THEN THE система SHALL заблокировать пуш с указанием
  причины отказа.
- **E3.** IF `HEAD` не отстаёт от базы, THEN THE система SHALL пропустить пуш без дальнейших проверок.
- **E4.** IF предсказание слияния сообщает о конфликте, THEN THE система SHALL заблокировать
  пуш, перечислить конфликтующие пути и SHALL NOT изменять рабочее дерево.
- **E5.** WHERE задан `empirical.test_command`, THE система SHALL выполнить его на смерженном
  дереве во временном worktree и заблокировать пуш при ненулевом коде или таймауте.
- **E6.** WHERE `empirical.test_command` не задан, THE система SHALL пропустить пуш с явной
  пометкой, что тесты на слиянии не выполнялись.
- **E7.** WHEN проверка завершается любым исходом, THE система SHALL удалить временный worktree.
- **E8.** IF задан аудируемый обход, THEN THE система SHALL пропустить пуш и записать причину.

## 8. Отвергнутые подходы

- **Автоматический pull/rebase перед пушем.** Мутация рабочего дерева за спиной человека:
  конфликт посреди грязного дерева, потеря контекста. Разрешение конфликта — не работа гейта.
- **Прогон тестов на ветке вместо слияния.** Не ловит С4 — единственный случай, ради которого
  гейт и нужен.
- **Проверка на SessionStart вместо pre-push.** База успевает уйти вперёд за время сессии;
  предупреждение в начале не блокирует пуш и легко теряется. Уместно как дополнение, не замена.
- **Инвалидация approve после вливания main.** Не нужна: §2 — merge-коммиты уже exempt,
  деплой-гейт commit-bound.

## 9. Документированный остаток

Гейт проверяет слияние с tip базы **на момент пуша**. Если база уедет между нашим пушем и
слиянием на GitHub, результат снова не проверен. Это принципиально не лечится локально —
серверная сторона живёт в inframon (см. `docs/2026-07-23-inframon-interface-design.md`).

## 10. Открытые вопросы

- Дефолт базы: `origin/main` жёстко или вывод из `origin/HEAD`.
- Таймаут fetch и таймаут тестов: свои значения или переиспользовать `empirical.timeout`.
- Нужен ли кэш «эта пара (base tip, HEAD) уже проверена», чтобы повторный пуш не гонял тесты снова.
