# Дизайн: деплой плагина gates на флот (0.10.0)

Сейчас обновление плагина — ручные слэш-команды на каждой машине. За две недели это трижды
приводило к тому, что машины разъезжались по версиям, и каждый раз молча:

* дев-сервер две недели работал на 0.9.3, пока `compute_tree` на маке был уже в 27 раз быстрее —
  заметили только по телеметрии, случайно;
* Codex-копия плагина отставала независимо от Claude-копии, и ревьюер слеп **четырежды**,
  возвращая «замечаний нет» с кодом 0;
* `/plugin update` при устаревшем каталоге печатает ПУСТОЙ вывод, неотличимый от «уже свежее».

Это тот же класс, что чинился весь месяц: **отказ выглядит как норма**. Деплой должен делать
разъезд версий невозможным и громким.

## 1. Задача

`make deploy` в репозитории плагина: привести ВСЕ машины флота к `origin/main`, проверить это
на каждой и уметь вернуться, если выкатка сломала гейты.

Особенность, определяющая дизайн: **сломанный плагин ломает гейты, а гейты fail-closed** —
то есть неудачный деплой блокирует коммиты на всех машинах сразу. Откат тут не украшение.

## 2. Подход

### Р1. Pre-deploy гейт (любой красный шаг останавливает выкатку)

1. **Чистое дерево** — `git status --porcelain` пуст.
2. **Тесты зелёные** — `pytest`.
3. **`HEAD == origin/main`.** Специфика этого деплоя: машины ставят плагин ИЗ GITHUB, поэтому
   выкатить незамерженное физически нельзя. Проверка явная, иначе оператор увидит «деплой
   прошёл», а на хостах окажется прошлый коммит.
4. **Версия согласована в трёх манифестах** (`plugin.json`, `.codex-plugin/plugin.json`,
   `marketplace.json`) и отличается от уже задеплоенной хотя бы на одном хосте — иначе
   «деплой» ничего не меняет, а выглядит успешным.

Пункты 3–4 — не бюрократия: оба сценария уже случались в этой работе.

### Р2. Обе стороны плагина, а не только Claude

На каждом хосте обновляются ОБА канала:

* Claude: `claude plugin marketplace update` → `claude plugin update`;
* Codex (если `codex` на хосте есть): `codex plugin marketplace upgrade` → `codex plugin add`.

Codex-копия отставала независимо и делала обязательного ревьюера слепым. Разделять их —
значит воспроизводить тот же инцидент.

### Р3. Пост-деплой верификация на КАЖДОМ хосте — по поведению, а не по слову CLI

Мало «команда сказала updated». Проверяем:

1. `installed_plugins.json` даёт ожидаемую версию И `gitCommitSha == origin/main`;
2. шим (`gates-run`) резолвится в каталог этой версии;
3. **живой smoke: `compute_tree` во временном репозитории равен `git add -A`.** Это сильнейшая
   доступная проверка — ровно тот инвариант, на котором держится лесенка, и стоит она ~300 мс.
   «Скрипт импортируется» такой гарантии не даёт;
4. Codex-канал (где есть): установленная версия совпадает с ожидаемой.

Структурная проблема хоть на одном хосте → ненулевой код и явный список, что не так.

### Р4. Снапшот, автооткат, ручное восстановление

* **Снапшот до мутации:** запись `installed_plugins.json` для плагина сохраняется в
  `.deploy-state/<host>-<timestamp>.json` вместе с версией и путём.
* **Откат возможен, потому что кэш версионный:** предыдущие каталоги
  (`cache/lenar-gates/gates/0.9.3/…`) остаются на диске. Проверено: шим резолвит по
  `installPath`, и возврат записи на прошлую версию возвращает рабочие скрипты.
* **Автооткат при СТРУКТУРНОМ провале** верификации: вернуть запись на снапшот, прогнать ту же
  верификацию ещё раз. Если откат не удался — громкий текст с путём к снапшоту и явной командой.
* **`make gates-restore HOST=… VERSION=…`** — escape-hatch и обычный способ вернуться.
* **Персист «стабильной» версии только ПОСЛЕ верификации:** файл `.deploy-state/stable` пишется
  в самом конце, когда все хосты зелёные.

Оговорка честная: откат перенаправляет метаданные харнесса на прошлую версию из кэша. Это
восстанавливает СКРИПТЫ ГЕЙТА (то, что деплой и трогает) немедленно. Долговременный фикс —
`git revert` + новый деплой; так и написано в тексте отката.

### Р5. Конфигурация флота

`.env.deploy` (gitignore) + `.env.deploy.example`, как требует стандарт: параметры деплоя
отдельно от рантайм-секретов. Содержит только список хостов:
`GATES_HOSTS="local smartape-vps-1"`. `local` — эта машина без ssh.

Паролей нет и быть не может: ssh только по ключу из `~/.ssh/config` (правило CLAUDE.md).

### Что НЕ делается

* **Не трогается логика гейтов.** Деплой — инструмент репозитория (Makefile + скрипт), а не
  часть плагина: по записанной границе плагин это локальные гейты, а флот — не его дело.
* **Нет автодеплоя по push.** Выкатку запускает человек: гейты fail-closed, и автоматическая
  выкатка сломанной версии заблокировала бы работу на всех машинах сразу.
* **Не деплоится незамерженное** (см. Р1.3).

## 3. Файлы

`Makefile` (цели `check`, `deploy`, `gates-restore`, `deploy-status`),
`scripts/deploy_gates.py` (логика), `.env.deploy.example`, `.gitignore`,
`tests/test_deploy.py`, `CHANGELOG.md`, версия 0.10.0.

## 4. Инварианты

* Пароль никогда не идёт аргументом командной строки — только ssh по ключу.
* Деплой только из чистого дерева, с бэкапом и автооткатом (CLAUDE.md).
* Верификация — на КАЖДОМ хосте, по поведению.
* Исключения не глотать: ошибка ssh/CLI — это отказ деплоя, а не «хост пропущен».
* Каждый новый code path — тест, реально входящий в эту ветку.

## 5. BSAC

| # | Сценарий | Как проверяется |
|---|---|---|
| S1 | Грязное дерево / красные тесты / `HEAD != origin/main` → деплой НЕ начинается | тест на каждый из трёх |
| S2 | Рассогласованные версии в трёх манифестах → отказ до выкатки | тест |
| S3 | Успешный деплой: на всех хостах версия и sha совпадают с `origin/main` | тест на фейковых хостах |
| S4 | Верификация ловит хост, где CLI отчитался успехом, а версия НЕ обновилась | тест: подменённый ответ |
| S5 | **Smoke по поведению**: подменённый (сломанный) скрипт на хосте → верификация красная | тест: `compute_tree` ≠ `git add -A` |
| S6 | Структурный провал на ОДНОМ хосте → автооткат на нём, ненулевой код, список проблем | тест |
| S7 | Провал самого отката → громкий текст с путём к снапшоту и командой восстановления | тест |
| S8 | `make gates-restore` возвращает прошлую версию, и шим её резолвит | тест |
| S9 | Codex-канал обновляется и проверяется там, где `codex` есть; отсутствие `codex` — не ошибка | тест на обоих вариантах |
| S10 | Ошибка ssh не «пропускает» хост молча | тест |
| S11 | «Стабильная» версия пишется только после зелёной верификации ВСЕХ хостов | тест: один хост красный → `stable` не изменился |

### Денежные / актуаторные краевые случаи

Прямых денег нет; поверхность — гейты, которые защищают деплой боевых проектов.

| # | Риск | Как предотвращается |
|---|---|---|
| M1 | Деплой выкатывает сломанную версию на все машины разом → гейты fail-closed → работа встала везде | Верификация по поведению + автооткат на каждом хосте; `stable` пишется последним. S5–S7 |
| M2 | Деплой «прошёл», а хост остался на старой версии — и разъезд снова замечают случайно | Верификация сверяет ВЕРСИЮ И sha, а не вывод CLI. S4 |
| M3 | Codex-копия отстаёт независимо, ревьюер слепнет и возвращает «замечаний нет» | Оба канала в одном деплое. S9 |
| M4 | Откат перенаправил метаданные, а харнесс их перезапишет при следующем `update` | Откат — временная мера, это сказано в его же тексте; долговременный фикс `git revert` + деплой |
| M5 | Пароль/секрет утечёт в лог деплоя | Паролей нет: только ssh по ключу; в логах — имена хостов и версии |
| M6 | Автооткат сработает на КРАСНОЙ ПРИКЛАДНОЙ проверке и откатит здоровый деплой | Триггер отката — только структурные проблемы (версия/sha/резолв/smoke), как требует стандарт |
