# Третий проход лесенки: `security` — дизайн

**Дата:** 2026-07-25. **Статус:** design (на ревью). **Tier:** 2 (правка `DEPLOY_REQUIRED_PASSES` —
канонической константы деплой-гейта; ошибка в обе стороны дорога: fail-open = security-проход не
требуется, fail-safe = деплой заблокирован во ВСЕХ онбордженных проектах).

## Мотив (почему существующего security-слоя недостаточно)

Плагин Claude `security-guidance` v2.0.6 даёт три слоя: regex-предупреждения на Edit/Write,
LLM-ревью диффа на Stop (по умолчанию Opus), агентное ревью на `git commit`/`git push`. Но:
- он **post-hoc и совещательный**: хуки `PostToolUse` + `asyncRewake` — коммит уже состоялся,
  находки приходят после; ничто не блокирует;
- он **не оставляет следа**, который знал бы деплой-гейт: можно получить «high: command
  injection», проигнорировать и задеплоить — гейт об этом не узнает;
- слой LLM-ревью идёт на Claude-модели → **то же семейство, что автор кода**: ценная линза, но
  НЕ независимость.

Ровно та же логика уже сделала обязательными `/simplify` и `/code-review`: лесенка доказывает,
что **шаг выполнен на финальном коде**, а честность обеспечивает независимое ревью. Реальный
пример из этой сессии: `shell=True` в `_run_empirical` поднял именно security-слой, а
адверсариальное Codex-ревью того же кода этого не подняло (оно нашло fail-open в логике) —
разные линзы находят разное.

## Что делаем

`DEPLOY_REQUIRED_PASSES = ("simplify", "code-review", "security")` — третий проход в цепочке.
Порядок канонический: **simplify → code-review → security**, security последний (его фиксы =
финальное состояние; их, как и раньше, ревьюит независимый гейт).

**Как выполняется проход:** `/security-review` (встроенная команда — запускает пользователь;
если она доступна модели — Claude) ЛИБО документированный security-фокус-проход по конституции
(класс «внешний ввод → опасный сток», секреты, авторизация, слабая криптография). Как и два
других прохода, он **self-attested**: лесенка доказывает «шаг выполнен на этом дереве», не
«выполнен честно».

**Протокол — существующий, без новых механик:** `begin security` (снимает `tree_before`,
валидирует старт цепочки против `code-review.tree_after`) → проход → `mark security` (пишет
маркер, consume-then-publish, анти-replay). `check-precommit` валидирует полную цепочку:
`simplify.after == code-review.before` И `code-review.after == security.before` И
`security.after == индекс`.

## Обратная совместимость — главный край (иначе фича ломает все проекты)

Наивное добавление третьего прохода делает НЕВАЛИДНЫМИ все существующие ledger-записи
(`passes: ["simplify","code-review"]`) → `check_range` блокирует деплой на всей пост-эпоховой
истории каждого онбордженного проекта. Это fail-SAFE, но неприемлемо дорого.

**Решение — grandfathering по ПРОИСХОЖДЕНИЮ записи (не по конфигу, не по дате):**
post-commit нового кода пишет в запись `ladder_schema: 2`; валидация на деплое:
- запись с `ladder_schema >= 2` → требуется ТЕКУЩИЙ канонический набор (3 прохода);
- запись **без** `ladder_schema` (легаси — её физически писал старый код, когда security-прохода
  не существовало) → требуется ЛЕГАСИ-набор (`simplify`, `code-review`).

Почему это не дыра: запись создаёт наш собственный post-commit хук; новый код не может выпустить
легаси-запись, а коммит, сделанный до фичи, не мог иметь security-проход. Ручная правка ledger —
тот же класс «осознанный обход» (ledger локален и gitignored), что и правка маркера.

**Остаток (документируем):** разработчик со СТАРОЙ установленной версией плагина продолжает
писать легаси-записи → security молча не требуется для его коммитов. Тот же класс version-skew,
что уже задокументирован для шимов; авторитетное закрытие — серверная сторона (inframon).

## Scenario-first: пространство входов (ТЕКСТ до кода)

Измерения:
- **D1 набор маркеров в сессии**: {нет, только simplify, simplify+code-review, все три}
- **D2 цепочка деревьев**: {валидна, разрыв simplify→code-review, разрыв code-review→security,
  security.after ≠ индекс}
- **D3 состав коммита**: {код, только не-код (docs)}
- **D4 запись ledger на деплое**: {schema≥2 с 3 проходами, schema≥2 с 2 проходами, легаси с 2,
  легаси с 1, exempt-noncode, skipped, отсутствует}
- **D5 конфиг `ladder.required_passes`**: {отсутствует, урезанный}
- **D6 эпоха/merge**: {коммит-предок epoch, merge-коммит, обычный пост-эпоховый}
- **D7 `LADDER_SKIP`**: {не задан, `1`}

| # | Условие | Ожидание |
|---|---|---|
| SEC1 | все три маркера, цепочка валидна, код-коммит | pre-commit 0; ledger: 3 прохода + `ladder_schema: 2` |
| SEC2 | только simplify+code-review (нет security), код-коммит | pre-commit **БЛОК** + инструкция с полным протоколом (вкл. security) |
| SEC3 | `begin security` при tree ≠ `code-review.tree_after` | ошибка «сначала /code-review» (ручная правка между проходами) |
| SEC4 | `mark security` без `begin` / повторный mark | ошибка (существующий анти-replay R7) |
| SEC5 | докс-коммит (не-код) | exempt, проходы не нужны (существующее) |
| SEC6 | `LADDER_SKIP=1` | pre-commit пропуск + аудит; post-commit пишет `skipped` (существующее) |
| SEC7 | деплой: запись `schema=2`, 3 прохода, tree совпал | покрыт |
| SEC8 | деплой: запись `schema=2`, только 2 прохода | **БЛОК** (новая запись обязана иметь канонический набор) |
| SEC9 | деплой: ЛЕГАСИ-запись (нет `ladder_schema`), 2 прохода, tree совпал | **покрыт** (grandfathering по происхождению) |
| SEC10 | деплой: легаси-запись с 1 проходом | **БЛОК** (даже легаси-набор не полон) |
| SEC11 | `ladder.required_passes: [simplify]` в конфиге + запись с 1 проходом | деплой **БЛОК** — канонический набор из КОДА, конфиг не ослабляет (существующий инвариант ML-L7, регресс) |
| SEC12 | коммит — предок `epoch_sha`, записи нет | покрыт (grandfathering эпохи, существующее) |
| SEC13 | merge-коммит без записи | покрыт с громкой пометкой (существующее) |
| SEC14 | запись `exempt-noncode` + `schema=2`, tree совпал | покрыт |
| SEC15 | запись `skipped: true`, tree совпал | покрыт + громкий аудит; в вердикте `ladder: covered-with-skips` (существующее) |
| SEC16 | деплой: записи нет вовсе (пост-эпоховый код-коммит) | **БЛОК** (существующее) |

Полнота: каждое значение D1–D7 встречается; ключевые комбинации — цепочка×разрыв (SEC2/SEC3),
schema×полнота набора (SEC7–SEC10 — сердце обратной совместимости), конфиг не ослабляет (SEC11),
существующие exempt-пути не сломаны (SEC5, SEC12–SEC15).

Осознанно ВНЕ scope: проверка, что security-проход выполнен «честно» (self-attested, как и два
других — честность даёт независимое ревью); автоматический запуск `/security-review` из гейта
(это команда харнесса, не наша); отдельный security-статус в вердикте для inframon (`ladder`
уже несёт covered/covered-with-skips/skipped — новое поле добавит контракт без потребителя).

## EARS

- **EARS-1:** `DEPLOY_REQUIRED_PASSES` SHALL быть `("simplify", "code-review", "security")` —
  константа КОДА, не конфиг. (SEC7, SEC11)
- **EARS-2:** `begin security` SHALL валидировать, что текущее дерево == `code-review.tree_after`;
  иначе ошибка. (SEC3)
- **EARS-3:** `check-precommit` SHALL требовать полную цепочку трёх проходов до индекса; при
  разрыве/отсутствии — abort с инструкцией, включающей security-шаг. (SEC1, SEC2)
- **EARS-4:** post-commit SHALL писать `ladder_schema: 2` во ВСЕ типы записей (полная, exempt,
  skipped). (SEC1, SEC14, SEC15)
- **EARS-5:** `check_range` SHALL валидировать запись против набора, определяемого её
  происхождением: `ladder_schema >= 2` → текущий канонический набор; отсутствие поля → легаси-набор
  (`simplify`, `code-review`). (SEC7–SEC10)
- **EARS-6:** Существующие exempt-пути (не-код, epoch-предок, merge-коммит, skipped) SHALL
  работать без изменений. (SEC5, SEC12–SEC15)
- **EARS-7:** Урезание `ladder.required_passes` в конфиге SHALL НЕ ослаблять деплой-проверку. (SEC11)

## BSAC

- **BS-S1:** код-коммит невозможен без выполненного security-прохода на финальном коде. (SEC1, SEC2)
- **BS-S2:** деплой невозможен, если у пост-фичевого код-коммита диапазона нет security в записи. (SEC8)
- **BS-S3:** фича НЕ ломает существующие проекты: коммиты, сделанные до неё, остаются покрытыми. (SEC9)

Краевые случаи:
- **ML-S1 [fail-open]** security-проход не требуется, потому что запись «выглядит легаси». →
  Провенанс: легаси-набор принимается ТОЛЬКО при отсутствии `ladder_schema`, а новый код всегда
  его пишет. Остаток — старая установленная версия плагина (version-skew, см. выше).
- **ML-S2 [fail-safe, дорогой]** все существующие проекты блокируются на деплое. → EARS-5
  grandfathering по происхождению (SEC9).
- **ML-S3 [fail-open]** конфиг `required_passes` урезан → security не требуется. → EARS-7,
  канонический набор в коде (существующий инвариант, покрыт регрессом SEC11).
- **ML-S4 [трение]** три обязательных прохода на каждый код-коммит. → Осознанно: security-класс
  дороже пропустить, чем прогнать; docs-коммиты exempt; аварийный путь — audited `LADDER_SKIP`.

## Отвергнутые альтернативы

- **Требовать security только для «security-чувствительных путей» из конфига.** Отвергнуто:
  новая поверхность ослабления через конфиг (пришлось бы pin-механику, как для `deploy`-секции),
  а классификация «чувствительный путь» ненадёжна — инъекция приходит там, где не ждали.
- **Grandfathering по дате/таймстампу записи.** Отвергнуто: таймстамп локален и правится; провенанс
  (наличие поля схемы) честнее и не требует доверять часам.
- **Новая эпоха `security_epoch_sha` в конфиге.** Отвергнуто: конфиг-поверхность + требует ручной
  настройки в каждом проекте; провенанс записи даёт то же бесплатно.
- **Полагаться на плагин `security-guidance` как на энфорсмент.** Отвергнуто: post-hoc,
  совещательный, без следа для деплой-гейта, и на Claude-модели (не независимость).
- **Опрашивать `security-guidance` о его находках.** Отвергнуто: его вывод — не контракт (нет
  стабильного машинного формата/файла), а перехват чужого хука хрупок.

## Тестирование

Юнит (tmp git-репо, как существующие ladder-тесты): SEC1–SEC16. Явно: полная трёхзвенная цепочка
(SEC1 — маркеры и ledger с `ladder_schema`); блок без security (SEC2); `begin security` против
разрыва (SEC3); **сердце совместимости** — легаси-запись без схемы с 2 проходами покрыта (SEC9),
а `schema=2` с 2 проходами блокирует (SEC8); конфиг не ослабляет (SEC11). Регресс: ВСЕ
существующие ladder-тесты и тесты деплой-гейта зелёные (двухзвенные цепочки в них надо
переписать на трёхзвенные — это ожидаемый RED от смены канонического набора).
