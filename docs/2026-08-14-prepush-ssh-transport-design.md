# Дизайн: pre-push гейт неисполним по SSH — нейтрализация убивает сам транспорт (0.9.2)

Обнаружено при попытке запушить фикс 0.9.1: **любой пуш в SSH-ремоут блокируется гейтом**,
единственный выход — `INTEGRATION_SKIP=1`. Тот же класс, что инцидент
`BUG-0.9.0-symlink-tree-hash`: гейт не строгий, а физически непроходимый, и подсказка в
тексте хука ведёт прямо к обходу.

## 1. Задача

### Симптом

```
$ git push -u origin fix/tree-hash-from-index
[prepush] ✗ refs/heads/fix/...: база не обновлена (fatal: cannot exec '/nonexistent':
          No such file or directory ... fatal: unable to fork) — блок (политика
          on_fetch_failure=block)
error: failed to push some refs
```

При этом обычный `git fetch origin main` в том же репозитории отрабатывает за доли секунды.

### Корень

`prepush_gate.py`, `_prepush_fetch` (строки ~55-82). Адаптер сознательно снимает
`protocol.allow=never` (иначе fetch невозможен по построению) и валидирует URL, но остальную
нейтрализацию оставляет как есть — включая `-c core.sshCommand=/nonexistent` из
`_GIT_NEUTRALIZE`. Для SSH-транспорта это и есть команда транспорта: git обязан её запустить.

Проверено, единственная изменённая переменная — значение `core.sshCommand`:

| `core.sshCommand` | rc | stderr |
|---|---|---|
| `/nonexistent` (сейчас) | 128 | `fatal: cannot exec '/nonexistent'` |
| `/usr/bin/ssh` | **0** | — |

Всё прочее (абсолютный бинарь, аллоулист окружения, `--upload-pack git-upload-pack`,
`core.gitProxy=`, отклонение `remote.<name>.vcs`, запрет `ext::`) не трогалось.

**Кого задевает:** любой репозиторий с SSH-ремоутом, то есть подавляющее большинство. Гейт
не «строгий» — он не может отработать ни при каких данных.

**Почему не заметили раньше:** политика по умолчанию `on_fetch_failure=block` даёт корректный
на вид отказ «база не обновлена», неотличимый от настоящей несвежей базы. Отказ движка снова
выглядит как честный вердикт — ровно диагноз, который уже разбирался в 0.9.1 для лесенки.

### Ошибка уровня, а не строчки

`_GIT_NEUTRALIZE` гасит исполняемые конфиги, ПОДСТАВЛЯЯ несуществующий путь. Для конфигов,
которые git исполняет факультативно (`gpg.program`, `core.editor`, `core.askPass`,
`diff.external`), это верно: они не нужны, и пусть падают. Но `core.sshCommand` при
SSH-транспорте — не факультативная украшательская команда, а **сам транспорт**. Гашение
подменяет «проверяемая сторона не выберет команду» на «команду не запустить вовсе».

Правило верного уровня: **исполняемое, без которого операция невозможна, не отключают —
его ПРИКРЕПЛЯЮТ к доверенному абсолютному пути.** В этом же файле такой приём уже применён к
`--upload-pack git-upload-pack` (командная строка перебивает `remote.<name>.uploadpack`), и
к самому git — `_trusted_git_bin()`. `core.sshCommand` просто выпал из списка.

### Ревизия 2 (после дизайн-ревью Codex)

Ревью нашло две вещи, обе проверены эмпирически; одна оказалась настоящей дырой, вторая —
верным замечанием о недоказанном свойстве.

**`GIT_SSH_COMMAND` перебивает `-c core.sshCommand` — но до адаптера не доезжает.** Проверено
рекордером: подсунутая переменная действительно исполняется вместо закреплённого ssh
(`рекордер запущен: True`), а `GIT_SSH` и `GIT_CONFIG_PARAMETERS` — нет. Окружение адаптера
строится АЛЛОУЛИСТОМ `_GIT_ENV_ALLOW` = `(USER, LOGNAME, LANG, LC_ALL, LC_CTYPE, TZ)`, и
`GIT_SSH_COMMAND` в нём отсутствует, поэтому свойство держится уже сегодня. Дыры нет —
но нет и теста, а свойство несущее: добавь кто-нибудь переменную в аллоулист «чтобы
заработало в CI», и закрепление молча умрёт. Поэтому переменные гасятся ЯВНО и покрываются
чёрным ящиком.

**Относительный путь из доверенного конфига исполняется из репозитория — подтверждено.**
Fetch выполнялся с `cwd` = корень репозитория, поэтому относительная команда
(`ProxyCommand ./proxy` в `~/.ssh/config`, `core.sshCommand=./x`) резолвится в байты
ПРОВЕРЯЕМОЙ стороны и запускается:

| cwd | относительная команда исполнилась из репо |
|---|---|
| корень репозитория (сейчас) | **да** |
| нейтральный + `--git-dir` | нет |

Это реальный вектор repo-local исполнения, и он шире, чем ssh: любой относительный путь в
любом конфиге, который читает git или ssh. Закрывается не перечислением директив OpenSSH, а
сменой cwd — то есть на верном уровне.

## 2. Подход

`_prepush_fetch` подставляет `-c core.sshCommand=<абсолютный ssh из доверенных каталогов>`
вместо `/nonexistent`. Резолв — тем же способом, что `_trusted_git_bin` резолвит git:
перебор `_TRUSTED_PATH_DIRS`, `resolve(strict=True)`, проверка «файл + исполняемый + НЕ внутри
репозитория».

```python
def _trusted_ssh_bin() -> "str | None":
    """Абсолютный ssh из доверенных каталогов — тем же правилом, что _trusted_git_bin."""
```

- Нашли → `core.sshCommand=<путь>`; подмена команды проверяемой стороной по-прежнему
  невозможна (командная строка перебивает и локальный, и глобальный конфиг).
- Не нашли → оставляем `/nonexistent` и **говорим об этом прямо** в причине отказа: сейчас
  оператор видит `cannot exec '/nonexistent'` и не может понять, что это политика гейта,
  а не поломка его машины.

### Р2. Fetch выполняется из НЕЙТРАЛЬНОГО каталога

`cwd` адаптера меняется с корня репозитория на `_trusted_home()`, репозиторий указывается
явно: `git --git-dir=<root>/.git fetch ...`. Проверено: связка «нейтральный cwd + `--git-dir` +
закреплённый ssh» даёт `rc=0` и обновляет `FETCH_HEAD`, а относительная команда из конфига
при этом уже НЕ исполняется из репозитория.

Это и есть ответ на вопрос ревью о границе доверия, и он лучше того, что было в ревизии 1.
`~/.ssh/config` остаётся территорией ВЛАДЕЛЬЦА МАШИНЫ — та же граница, что уже зафиксирована в
этом файле для локальных bare-репозиториев и в `_trusted_home()` (домашний каталог из БД
пользователей, а не из `$HOME`). Но перечислять исполняемые директивы OpenSSH (`ProxyCommand`,
`Match exec`, `KnownHostsCommand`, `LocalCommand`) и надеяться, что список полон, — это
денилист, который здесь уже не раз проигрывал. Смена cwd закрывает КЛАСС: ни один
относительный путь ни в одном конфиге не резолвится в байты проверяемой стороны, независимо от
того, какая программа его прочитала и какую директиву мы забыли.

### Р2b. Fetch идёт по ЯВНОМУ абсолютному URL, а не по имени ремоута

Находка раунда 2, подтверждена: относительный URL ремоута (`../base.git` — форма, которую
`_fetch_remote_allowed` разрешает намеренно) резолвится от **cwd процесса**. Сдвиг cwd из Р2
менял бы его смысл: здесь fetch просто упал (`rc=128`), но окажись по новому пути другой
репозиторий — гейт молча сверился бы с ЧУЖОЙ историей и сказал «база свежая». Fail-open,
внесённый моей же правкой.

Лечение снимает и причину, и класс: URL уже прочитан и провалидирован, поэтому в `fetch`
передаётся ОН САМ, приведённый к абсолютному пути относительно корня репозитория, — а не имя
ремоута. Проверено: из обоих cwd `rc=0` и `FETCH_HEAD` равен настоящему tip'у базы.

Побочная выгода: транспорт перестаёт зависеть от того, что репозиторный конфиг рассказывает
про имя `origin` в момент самого fetch.

### Р3. Переменные подмены транспорта гасятся явно

`GIT_SSH_COMMAND`, `GIT_SSH`, `GIT_SSH_VARIANT`, `GIT_CONFIG_PARAMETERS`, `GIT_CONFIG_COUNT`,
`GIT_PROXY_COMMAND` удаляются из окружения адаптера явно, хотя аллоулист их и так не
пропускает. Смысл — не в текущем поведении, а в том, чтобы правило было ВИДНО в точке, где
оно несущее: `GIT_SSH_COMMAND` имеет приоритет НАД `-c core.sshCommand` (проверено рекордером),
и расширение аллоулиста в будущем убило бы закрепление молча.

### Что НЕ делается и почему

**Идентичность базы по-прежнему берётся из конфига репозитория — это остаток, а не фикс.**
Проверено: `.git/config` может подтянуть `include.path = ../attacker.cfg` **из рабочего
дерева**, и включённый файл влияет на эффективный конфиг. Прямой обход валидации через
`url.*.insteadOf` при этом НЕ проходит — `git remote get-url` применяет `insteadOf` ДО нас,
поэтому подставленный `ext::` мы видим и отвергаем (проверено). Но перенаправить базу на
другой РАЗРЕШЁННЫЙ URL (свой https-хост) можно, и гейт сверится с чужой историей, считая её
базой.

Это не лечится санитизацией ключей: проверяемая сторона в принципе владеет `.git/config`.
Лечится только тем, что идентичность базы перестаёт браться оттуда — например, URL/ref базы
закрепляется в `.codex-gate.yaml`, который сам под ревью и в коммите. Это отдельный дизайн,
не догрузка к транспортному фиксу. В реестр остатков.

**HTTPS с приватным репозиторием — тот же класс, но не чинится здесь.** `credential.helper=`
погашен, `GIT_CONFIG_GLOBAL=/dev/null`, `GIT_TERMINAL_PROMPT=0` — значит приватный HTTPS-ремоут
тоже нечем аутентифицировать. Механизм другой (учётные данные, не команда), лечение другое
(доступ к глобальному конфигу владельца машины), а воспроизвести на этой машине нечем: ремоут
здесь SSH. Идёт в реестр остатков отдельной строкой, а не чинится вслепую.

**Исполняемые директивы OpenSSH не перечисляем.** Ревью предлагало либо нейтральный cwd, либо
гейт-owned ssh-конфиг без исполняемых директив. Второе — денилист по чужому, растущему набору
директив; в этом репозитории денилисты уже проигрывали четыре раза подряд. Берём первое.

**Политику `on_fetch_failure` не трогаем.** Она про доступность сети и работает верно;
проблема была в том, что fetch не мог отработать никогда.

## 4. Инварианты

- Стерильный git-слой: команда транспорта закрепляется абсолютным путём из доверенных
  каталогов, не берётся из конфига репозитория и не резолвится через PATH вызывающего.
- Fail-closed: ssh не найден → поведение как сейчас (блок), но с внятной причиной. Ни одна
  ветка не начинает пропускать пуш.
- Каждый новый code path — тест, реально входящий в эту ветку.

### Ловится ли баг тестом

S1 на текущем коде падает (`rc=128`, `cannot exec '/nonexistent'`). S3 — новый тест на
уже существующее свойство: он обязан быть зелёным и ДО, и ПОСЛЕ, потому что стережёт, чтобы
починка транспорта не открыла подмену команды. Это заявлено явно, а не выдаётся за регресс.

### Денежные / актуаторные краевые случаи

Прямых актуаторов нет. Денежная поверхность — косвенная, через ослабление гейта:

## 6. Архитектурный вывод (раунд 3) — исключён из сходимости

Три раунда дизайн-ревью нашли три экземпляра ОДНОГО корня: адаптер пытается санировать
конфиг проверяемой стороны ключ за ключом — гасит `core.sshCommand`, отклоняет
`remote.<name>.vcs`, пиннит `--upload-pack`, валидирует URL. Это денилист по чужой, растущей
поверхности; в этом репозитории денилисты проигрывали уже четырежды, и правило записано в
конституции. Он не сойдётся: раунд 1 — `GIT_SSH_COMMAND`, раунд 2 — `include.path` из
рабочего дерева, раунд 3 — двухступенчатый `insteadOf`.

**Проверено про раунд 3:** цепочка действительно обходит валидацию — `get-url` отдаёт
безобидный `git@github.com:…`, а при `fetch` второе правило переписывает его в `ext::`
(`fatal: transport 'ext' not allowed`). Но **произвольная команда НЕ исполняется**: git
блокирует транспорт `ext` собственной политикой. То есть это не RCE, а подтверждение свойства
«валидируем один URL, тянем другой». И свойство это **предсуществующее**: сегодняшний код
точно так же проверяет вывод `get-url`, а `fetch` делает по ИМЕНИ ремоута — через те же
правила переписывания.

**Правильное лечение — на уровне модели, не ключей:** сетевая операция должна идти в
ГЕЙТ-СОЗДАННОМ репозитории, который конфиг жертвы не читает вовсе
(`git init --bare <tmp>` + `GIT_CONFIG_GLOBAL=/dev/null` + `GIT_CONFIG_NOSYSTEM=1`). Проверено
на той же атаке: `rc=0`, команда не исполняется, `FETCH_HEAD` — настоящий tip базы. Тогда
разом отпадают `insteadOf`, `include.path`, репозиторный `sshCommand`, `vcs` и сам вопрос
«что ещё мы забыли погасить».

Почему не здесь: `merge-tree --write-tree` (предсказание слияния, §«merge_test») требует
объектов базы В РАБОЧЕМ репозитории, поэтому переезд сетевой операции в изолированный
репозиторий тянет за собой перенос всей проверки слияния. Это смена модели, а не догрузка к
транспортному фиксу. По стоп-политике архитектурные находки логируются и ИСКЛЮЧАЮТСЯ из
сходимости — цикл на этом закрывается.

**Что при этом ставится сейчас:** доступность (гейт снова исполним) плюс два реальных
сужения — репо-относительные команды больше не исполняются, репо-относительные URL больше не
переопределяются. Ни одно из них не ослабляет то, что есть сегодня.
