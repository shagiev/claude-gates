# Кросс-платформенность Claude ↔ Codex: пробелы к починке

Дата: 2026-07-30, ред. 2. Аудитория: агент, который будет это дочинивать (в т.ч. Codex).
Цель: чтобы **один плагин одинаково работал на обоих хостах**, а не патчился в каждом репозитории.

**Архитектурное решение после ревью:** G-3/G-4 в первоначальном виде с общим
`.claude/.host-session` отменены. Host и reviewer — независимые adapters; Cursor необязателен,
а blocking-модели допускаются через certification registry. Нормативная спека:
`docs/2026-07-30-cross-host-reviewer-architecture.md`.

**Как читать.** Раздел 1 — факты, снятые замером; на них можно опираться без перепроверки.
Раздел 2 — пробелы, каждый с механизмом (файл:строка), требованием и приёмкой. Раздел 3 — порядок
и ловушки, в которые я уже наступил. Раздел 4 — что НЕ измерено; там нельзя проектировать
без замера (цена уже выяснена: пять редакций одной спеки, четыре дефекта из пяти — «перенёс
механику, потеряв различение»).

## 1. Измеренные факты (Codex 0.145.0, замеры 26–30.07.2026)

**Хуки wire-совместимы с Claude Code.** События те же (`PreToolUse`, `PostToolUse`,
`SessionStart`, `UserPromptSubmit`, `Stop`, `SubagentStart/Stop`, плюс свои `PermissionRequest`,
`SessionEnd`, `PostCompact`). Формат конфига — `hooks.json` с внешней обёрткой `"hooks"`.

**Фактические поля `PreToolUse`** (снято живьём):

```
cwd, hook_event_name, model, permission_mode, session_id,
tool_input, tool_name, tool_use_id, transcript_path, turn_id
```

Полей `model` и `tool_use_id` в документации не было. `session_id` одинаков во всех событиях
прогона. **`model` называет модель автора прямо в payload'е** — единственный источник авторства,
который не является ни сниффингом окружения, ни объявлением оператора.

**`tool_input` различается по инструментам:**

| Инструмент | Claude Code | Codex |
|---|---|---|
| правка файла | `Edit`/`Write`, `{file_path: …}` | `apply_patch`, **`{command: "*** Begin Patch\n*** Add File: p.txt\n+…\n*** End Patch\n"}`** — ключа `file_path` НЕТ |
| shell | `Bash`, `{command: …}` | `Bash`, `{command: …}` — **совпадает** |

**Отказ работает:** хук с `exit 2` и текстом в stderr блокирует инструмент, и причина доходит до
модели дословно (`error=Command blocked by PreToolUse hook: <наш текст>`), после чего модель
объясняет её пользователю. Это именно то поведение, которое нужно G1.

**Барьер доверия — в КАТАЛОГЕ, а не в хуке.** Недоверенный каталог + любой файл хуков →
`codex exec` **висит бесконечно без единой строки диагностики** (проверено трижды: разные схемы,
оверрайд `trust_level` не помогает). После однократного интерактивного подтверждения (folder
trust + `/hooks` в TUI) неинтерактивные прогоны работают. Смена содержимого хука сбрасывает его
доверие (пиньуется по хэшу), но это покрывается флагом `--dangerously-bypass-hook-trust`;
недоверие каталогу не покрывается ничем из проверенного.

**Codex не выставляет переменную окружения с сессией.** `session_id` доступен ТОЛЬКО внутри
payload'а хука. Проверено замером окружения хука: из «сессионных» переменных там был лишь
`CLAUDE_CODE_SESSION_ID`, и это **утечка родительского процесса** (codex запускался из сессии
Claude Code), а не переменная Codex. Отсюда же вывод: определять хост по окружению нельзя.

**Упаковка Codex:** манифест `.codex-plugin/plugin.json` (в самом каталоге — только манифест;
`skills/`, `hooks/`, `assets/` в корне плагина), маркетплейс — `$REPO_ROOT/.agents/plugins/
marketplace.json` либо `~/.agents/plugins/…`, источники `local` / `git-subdir` / `npm`.
На Codex 0.145.0 отдельно измерено в чистом временном `CODEX_HOME`: marketplace с
`policy.installation: NOT_AVAILABLE` добавлялся и был виден как `not installed`, но
`codex plugin add gates@lenar-gates` завершался кодом 1 с `plugin gates is not available for
install`. 01.08.2026 entry опубликована как устанавливаемый preview (`AVAILABLE`) после
реализации G-4; portable deploy-review при отсутствии сертифицированного независимого backend
остаётся fail-closed. На Codex CLI 0.146.0 выполнен реальный install/activation smoke из
`lenar-gates`: установленный PreToolUse hook перехватил `apply_patch` тестового code-path,
вернул `exit 2` с `Command blocked by PreToolUse hook: Дизайн-ревью не пройдено…`, модель
остановилась, файл остался неизменным. Прогон использовал
`--dangerously-bypass-hook-trust` после верификации источника; manifest presence само по себе
не засчитывалось.

## 2. Пробелы

### G-1. `gate-edit` молча пропускает ВСЕ правки файлов под Codex — **критично**

**Механизм.** `codex_review_gate.py:1903-1906`:

```python
ti = data.get("tool_input") or {}
path = ti.get("file_path") or ti.get("notebook_path", "")
if not (path and is_code_path(path)):
    return 0                      # ← под Codex сюда попадает ВСЕГДА
```

Под Codex `tool_input` — это `{command: "*** Begin Patch …"}`, ключа `file_path` нет, `path`
пуст → ранний `return 0` → дизайн-гейт **не блокирует ничего** и при этом ничего не сообщает.
Гейт выглядит установленным и работающим.

**Требование.** Извлекать пути из конверта патча, когда `tool_name == "apply_patch"` (или когда
`file_path` отсутствует, а `command` похож на патч): строки `*** Add File: <p>`,
`*** Update File: <p>`, `*** Delete File: <p>`, плюс `*** Move to: <p>` при переименовании.
Путей может быть НЕСКОЛЬКО в одном патче — гейт должен срабатывать, если код-путём является
ХОТЯ БЫ один.

**Приёмка.** Тест с реальным конвертом (из §1) на добавление, изменение, удаление и патч,
меняющий сразу код-путь и не-код-путь → блок. Тест на патч, целиком не-кодовый → проход.
Мутация «вернуть только `file_path`» обязана убивать тест.

### G-2. Хуки для Codex не зарегистрированы вообще — **критично**

Ни в одном онбордженном репозитории нет `.codex/hooks.json`, а `.agents/` в Codex-репозитории
пуст. То есть даже после починки G-1 хуки не запустятся: их некому вызвать.

**Требование.** Два пути, и нужен как минимум один:
(а) **манифест плагина Codex** — `.codex-plugin/plugin.json` рядом с `.claude-plugin/plugin.json`,
общие `skills/` и `hooks/`, плюс `.agents/plugins/marketplace.json`; установка через
`codex plugin add`;
(б) **проектная регистрация** в `gates-init`: писать `<repo>/.codex/hooks.json`, указывающий на
скрипты плагина.

Путь (б) проще и работает уже сейчас (проверен замером), но требует шага доверия (см. G-5).
Путь (а) чище для распространения, но в нём НЕ проверено, выставляется ли `CLAUDE_PLUGIN_ROOT`
хукам, приехавшим из плагина (см. §4) — а вся наша `hooks.json` построена на этой переменной.

**Приёмка.** В онбордженном репозитории под Codex правка код-файла без дизайн-маркера
блокируется, и оператор видит причину; правка не-код-файла проходит.

### G-3. Сессия на ШЕЛЛ-пути под Codex отсутствует → атрибуция теряется — **средне**

**Уточнение к первоначальному диагнозу:** на хук-пути всё в порядке. `_hook_session`
(`codex_review_gate.py:1851`) уже устроен верно:

```python
return data.get("session_id") or _env_session()
```

то есть предпочитает `session_id` из payload'а. Ломается **шелл-путь**: `ladder_gate.mark`,
`write-marker`, аудит `LADDER_SKIP` берут сессию из `_env_session()`
(`ladder_gate.py:101-103`, `codex_review_gate.py:1667`), которая читает только `CLAUDE_*`.
Под Codex она пуста — отсюда в поле **все 10 записей ledger с пустым `session`**.

Проверено: валидацию цепочки это НЕ ломает (поле только пишется, нигде не сравнивается).
Последствие — потеря аудита, а не отказ.

**Требование (ред. 2).** Общий repo-wide `.host-session` запрещён: он подделываем и ломает
параллельные сессии. Сначала измерить поддержку Codex `updatedInput`; если она есть —
host-adapter безопасно добавляет session к точной shell-команде. Иначе используется одноразовый
per-command nonce/handoff. Session bridge обслуживает только G1/audit UX и никогда не разрешает
reviewer или deploy. Полный контракт — в cross-host reviewer architecture §5.

**Приёмка.** Под Codex `mark` и `LADDER_SKIP` пишут непустую сессию, совпадающую с `session_id`
из payload'а. Две параллельные сессии не получают id друг друга. Под Claude Code поведение не
меняется (переменная окружения по-прежнему главная).

### G-4. Независимость ревьюера: под Codex дефолт даёт саморевью — **критично по последствиям**

В поле: репозиторий, где код пишет Codex, имеет `REVIEW_PROVIDER ?= both` = `codex` + `cursor`,
то есть **половина панели того же семейства, что автор**. Спасает только вторая половина
(дефолтный `cursor-grok-*`, семейство xai). Существующий allow-list прибит к «бан `claude-*`»,
потому что писался в предположении «автор — Claude».

**Что важно:** это не лечится хардкодом наоборот. Две предыдущие попытки спеки провалили ревью
(`docs/2026-07-26-reviewer-independence-rule-design.md`, там разбор): «семейство хоста»
оказалось ненаблюдаемым в точке деплоя, а объявление оператора — подделываемым и привязанным к
машине, а не к репозиторию.

**Что изменилось после ревью:** достоверность `model` существует только внутри hook process.
Запись этого значения в repo-local файл снова делает его подделываемым и не доказывает множество
авторов истории. Поэтому наблюдение из hook может ужесточать правило, но не ослаблять
консервативный дефолт.

**Требование (ред. 2).** Reviewer-adapters используют общий строгий контракт. Универсальный
portable-режим считает возможными авторами `{anthropic, openai}` и допускает только
сертифицированное третье семейство. Cursor — optional; первый backend без Cursor — Gemini
headless JSON, далее direct xAI и сертифицированные local adapters. Claude/`auto` запрещены.
Точные фактические модели допускаются shipped certification registry, входят в audit/cache/verdict.
Нет независимого backend → deploy блокируется с инструкцией, без саморевью.

**Приёмка.** Пользователь без Cursor, но с сертифицированным Gemini, проходит deploy. Cursor
остаётся explicit legacy adapter до появления actual-model attestation. Mixed/unknown repo
допускает только третье семейство.
Unknown/сменившаяся модель, outage или отсутствие независимого reviewer блокируют. Полная
матрица — cross-host reviewer architecture §6.

**Статус 31.07.** Реализованы `ReviewerRun`, direct Gemini `generateContent` adapter со строгим
`modelVersion`, portable resolver, shipped registry/corpus/runner и обязательный Claude
supplemental artifact, не участвующий в blocking union. Gemini остаётся `candidate` до живого
corpus-прогона с API key. Cursor записан как `candidate`, но portable resolver намеренно вообще
не dispatch'ит его: JSON подтверждает requested slug, но не actual model; legacy adapter
сохранён, однако не считается certification evidence и не может быть включён простой сменой
registry status.
До promotion хотя бы одного независимого blocking adapter portable fail-closed блокируется.

### G-5. Онбординг Codex: обязательный интерактивный шаг и висящий CI — **средне**

`gates-init` ничего не знает про Codex. При этом (§1) недоверенный каталог + хуки = **зависание
без диагностики**, а не отказ.

**Требование.** `gates-init` должен: писать регистрацию хуков для Codex (G-2), печатать явную
инструкцию про однократное подтверждение (folder trust + `/hooks`), и предупреждать, что
headless-прогон в недоверенном каталоге **повиснет** — поэтому CI обязан либо иметь доверие
заранее, либо оборачивать вызов внешним таймаутом.

**Приёмка.** Свежий репозиторий под Codex: после `gates-init` и одного подтверждения G1
блокирует правку код-пути. Без подтверждения оператор получает написанное заранее предупреждение,
а не молчаливое зависание.

### G-6. Проходы лесенки называют команды, которых на платформе нет — **средне, честность записи**

В поле: 10 записей с `passes: [simplify, code-review, security]` в репозитории, где команд
`/simplify`, `/code-review`, `/security-review` **не существует** (они bundled/builtin у Claude
Code). Гейт различить «выполнили эквивалент» и «пометили» не может — это принятый остаток
закрытого тикета B1, но под Codex он становится нормой, а не краем.

**Требование.** Минимум: `_PASS_RUNNER` (`ladder_gate.py:50`) должен давать формулировку,
зависящую от **хоста** (из записи G-3), и не называть команды, которых на этом хосте нет.
Максимум — тема отдельной работы: чем на Codex выполняется каждый проход (у него есть свои
`codex exec review`, `/review`), и должен ли `mark` требовать хоть какого-то следа.

**Приёмка.** Под Codex `begin <проход>` печатает то, чем проход выполняется НА CODEX, а не
`/simplify`.

### G-7. Покрытие лесенки не переносится между рабочими копиями — **критично для деплоя**

Не кросс-платформенный, но обнаружен тем же анализом и бьёт по тому же месту.
`logs/` в `.gitignore`, поэтому ledger локален: в трёх рабочих копиях одного проекта
64 / 102 / 95 коммитов выглядят непокрытыми, хотя работа шла по протоколу — в соседнем каталоге.
Деплой-гейт из «неавторской» копии заблокирует диапазон целиком; в аудите это уже видно как
`CODEX_REVIEW_SKIP`.

**Требование.** Переносимое доказательство: трейлер коммита
(`Gates-Ladder: simplify,code-review,security`) путешествует с коммитом, переживает клонирование,
`cherry-pick` и ребейз (что закрывает и известный остаток «ребейз стирает покрытие»).
Подделываем ровно как локальный файл — в гарантиях не теряем, переносимость получаем.
Нужна спека: взаимодействие с `check_range`, grandfathering существующих записей, что считать
истиной при расхождении трейлера и ledger.

**Приёмка.** Свежий клон видит покрытие истории; `check_range` не требует локального ledger для
коммитов, несущих трейлер.

## 3. Порядок и ловушки

**Порядок обязателен, он не косметический:**

1. **G-1** (парсинг путей + matcher) — без него G1 бесполезен даже установленный.
2. **G-4** (reviewer protocol + Gemini + certification) — до доступной установки: иначе
   Codex-пакет включает ложный Codex→Codex deploy-review.
3. **G-2 + G-5** (регистрация, activation smoke test и онбординг) — только после G-4 перевести
   marketplace из `NOT_AVAILABLE` в `AVAILABLE`.
4. **G-3** (безопасный session bridge) — только после замера `updatedInput`.
5. **G-6** (host-specific UX) — на нормализованном host-adapter.
6. **G-7** (переносимое покрытие) — независимо, отдельной спекой.

**Ловушки, в которые я уже наступил:**

- **Не подменять session bridge общим файлом.** До безопасного моста G1 может пере-блокировать
  shell-команды, но это fail-safe и видно. Общий `.host-session` создаёт подделку/гонку и
  недопустим даже как временное решение.
- **Не ставить шим/хук раньше кода, который он вызывает.** Шим `pre-push`, положенный до
  обновления плагина, заблокировал ВСЕ пуши из репозитория; сообщение при этом диагностировало
  не ту причину. Порядок: сначала код в установленной версии, потом регистрация.
- **Не переиспользовать механику, теряя различение, на котором она держится.** Из пяти редакций
  спеки pre-push четыре дефекта были ровно этим: `absent` слит с `unreadable`, «база» вместо
  «предыдущего принятого tip'а», «команда задана» вместо «команда что-то проверяет».
- **Проверять вывод, а не только посылку.** Дважды за сессию механика подтверждалась
  экспериментом, а следствие оказывалось неверным.

## 4. Что НЕ измерено (здесь нельзя проектировать без замера)

- **Выставляется ли `CLAUDE_PLUGIN_ROOT` хукам, приехавшим ИЗ ПЛАГИНА Codex.** Доки утверждают,
  что да (алиас совместимости), замер проводился на ПРОЕКТНЫХ хуках и этого не подтверждает.
  Вся наша `hooks/hooks.json` построена на этой переменной, поэтому от ответа зависит,
  переезжает ли она в Codex дословно или требует второй версии.
- **Можно ли выдать доверие каталогу неинтерактивно** (для CI). Оверрайд `trust_level` через
  `-c` не помог, но проверялось на недоверенном каталоге и без folder-trust — возможны иные пути.
- **`hookSpecificOutput.permissionDecision: "deny"`** как альтернатива `exit 2` (exit 2 проверен
  и работает).
- **`PermissionRequest`** — своё событие Codex, потенциально более уместное для G1, чем
  `PreToolUse`. Поведение не проверялось.
- **Чем на Codex выполняется каждый проход лесенки** (см. G-6): есть `codex exec review` и
  `/review`, их пригодность как «прохода code-review» не оценивалась.
